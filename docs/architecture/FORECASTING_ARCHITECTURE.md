# Phase 2 Forecasting Service Contract

**Status:** internal Node API ↔ Python/FastAPI boundary; no ML algorithm chosen or service implemented. Forecasts are advisory, never gate/capacity/lifecycle commands.

The Node backend extracts ordered, authoritative accepted-attendance/occupancy observations and event context, applies an approved input window and minimization, and calls a versioned internal FastAPI endpoint over a protected service connection. Conceptual request: event or pseudonymous series ID, as-of timestamp, IANA zone, historical time/value/quality observations, single event registration capacity for comparison, fixed requested horizons `[30, 60]` minutes, relevant event schedule/context and method/version request. No name/contact/QR/OTP or raw scan payload. Server timestamps and transition provenance outrank client-supplied times.

Conceptual response: status `AVAILABLE`, `INSUFFICIENT_DATA`, `STALE_INPUT`, `MODEL_UNAVAILABLE`, or `INVALID_INPUT`; 30/60-minute predicted occupancy where available; interval or confidence/uncertainty representation with method; input window and last observation time; generation timestamp; method/model version and quality/limitation notes. Node validates schema, horizon completeness, plausibility, version and freshness, stores a versioned run/result, and exposes it only to authorized Organizer/Admin alongside current observed INSIDE occupancy, one capacity and age. A stale/invalid response is not silently displayed as current. No forecast can update attendance or block entry.

Use bounded timeout, no unbounded synchronous retry and an explicit degraded/unavailable state on timeout/service outage. Cached last-known result may be shown **only** with its generation time/stale label. Request cadence, window, minimum-data rule, timeout budget, cache duration and confidence method remain technical decisions supported by workload/data evidence. The command center remains usable when AI is unavailable.

Evaluation requires a simple baseline, chronological train/validation/test splits (no future leakage), reproducible versions/data, MAE/RMSE or justified metrics per 30/60-minute horizon, availability/coverage and uncertainty calibration where applicable. Compare any later model to the baseline; production acceptance threshold is deferred to the forecasting phase. pytest tests cover ordering, missing/sparse/late/duplicate observations, staleness, contract versions, timeout fallback and no PII/control output.
