## Transaction and constraint design to prove before schema

Registration uses event-scoped serialization or equivalent under concurrent capacity claims, plus conditional uniqueness for REGISTERED user/event and verified guest email **or** phone/event. Opening/closing is derived from event lifecycle, configured times, REGISTERED count and manual flag; capacity-only closure lifts after pre-check-in cancellation only if every other condition permits. Scan processing locks/serializes current credential/registration/attendance, enforces unique scan ID and one accepted transition, and persists critical audit/publication intent in the same transaction. Event cancellation and registration cancellation cannot race into an accepted post-cancel check-in. Corrections append a transition, never update historical transition rows. Alert condition uniqueness applies to the unresolved active condition (including acknowledged persistence) and re-arms only after resolution and a new occurrence. Certificate issue has unique issue identity per registration and unique certificate ID; batch selection/claim and delivery attempts need bounded concurrency and durable idempotency. Exact SQL constraints, isolation levels, audit fail-safe policy and retention windows are implementation decisions requiring concurrency tests, not schema assumptions.

Slice 3 event/gate/link writes use the event revision precondition where specified by the [API contract](../api/API_CONTRACT.md); required state change and audit must commit atomically. PRIVATE proof reissue must atomically revoke the old proof and establish the replacement under the one-active constraint. A same-key issuance retry returns the protected replay result without creating another proof. These are conceptual constraints, not a Prisma schema or migration in this documentation phase.
