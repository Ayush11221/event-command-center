# Phase 2 API Contract

## OTP aggregate admission (P0-E)

Both account and guest challenge endpoints reserve shared PostgreSQL CONTACT, SOURCE and PROVIDER request budgets before creating a challenge. Account existence, delivery purpose and delivery outcome never change admission accounting. Aggregate denial returns `429 {code: "RATE_LIMITED", message: "Too many verification requests. Please try again later.", correlation_id}` without the limiting category, counts, keys, contact/source identifiers, provider quota or retry timing. Unavailable admission state or unverifiable configured proxy metadata returns existing `503 DEPENDENCY_UNAVAILABLE`, `retryable:true`; no OTP is sent. Account requests admitted during the existing sixty-second cooldown retain generic `202`; guest cooldown retains its existing `429`. Verification/session/role contracts remain unchanged. Limits, proxy trust and retention are documented in [OTP abuse protection](../security/OTP_ABUSE_PROTECTION.md).

EMAIL challenge admission requires a single bare mailbox; SMTP display names, lists, comments, quoting, backslashes and control characters are `400 VALIDATION`. Equivalent IDNA domain spellings share the aggregate contact budget without changing existing account identity hashes.

## Team & Staff and camera capture (P0-C / P0-D)

Staff management uses the existing GET/POST/DELETE `/api/v1/events/{eventId}/assignments` operations and unchanged server policy: the owner manages all existing staff roles; an active Event Admin can read/manage Gate/Security and Volunteer assignments only. Self-grants, unverified targets, cross-event gates and unauthorized callers remain rejected. GET retains its existing assignment fields and adds `email:string|null` (verified email only) and top-level `allowed_roles:StaffRole[]` derived from current authority. It returns no session, OTP, contact hash/ciphertext or QR fields.

POST `/api/v1/events/{eventId}/assignments/account-lookup` accepts exactly `{email:string}`. Account authentication, existing Origin/CSRF checks and event staff-read authority precede the exact normalized EMAIL/HMAC lookup. Response is `200 {account:{user_id,email}|null,correlation_id}`; missing/unverified email returns null, self-selection is `403 SELF_ASSIGNMENT`, malformed/extra fields are `400 VALIDATION`. No prefix/wildcard search, pagination, public directory or account creation exists. Required `STAFF_ACCOUNT_LOOKUP` audit records actor/event/outcome without the searched contact, hashes or identity result; audit/DB failure returns 503 and no identity. Staff responses use private/no-store and no-referrer.

Gates currently have no stored display name. UI gate labels are deterministic `Gate 1`, `Gate 2`, etc., ordered by gate ID without displaying that ID. Existing authorized gate-scope GET adds only `event_name` and `gate_label`; it does not grant scanner authority. The scanner still selects only current Gate/Security assignments from account self and verifies each selected event/gate. Actual scan authority is independently rechecked by the unchanged scan-decision service.

Team role/gate changes revoke then grant via the existing APIs; there is no PATCH or new role system. These assignment mutations have no replay-key contract. Unknown results are held and reconciled with an authorized list read, never automatically resubmitted. An unknown revoke must be confirmed absent before the user can continue its replacement grant. Failed replacement is explicitly partial; role regrant does not transfer volunteer tasks bound to the previous assignment.

Camera capture requests rear-camera video only after Start camera, decodes QR frames locally with a lazy-loaded QR reader, and forwards only the opaque decoded value to the existing `/scan-decisions` client. No camera frames leave the device. Stationary QR values remain suppressed; a value must change or leave view for at least 1.2 seconds before another attempt. Each actual attempt creates one scan_id; unknown scans block further captures/manual submissions and retry the exact original command. Tracks/timers stop on Stop camera, hidden page, pagehide, gate switch and unmount; late permission grants are released. Denied/missing/unavailable cameras have manual entry fallback. Browser capture never validates credentials or grants authorization; server eligibility, idempotency, audits and all P0-A/P0-B session/OTP protections are unchanged. Physical-device acceptance remains a separate validation gate.

## Account identity foundation (P0-A / P0-B)

One account entry supports sign-in and ordinary account creation through verified email. `POST /api/v1/auth/account/challenge` accepts only `{type, contact}`; `POST /api/v1/auth/account/verify` accepts only `{type, contact, code}`. EMAIL is normalized by the existing contact rules. Both existing and new emails receive the same generic `202 {status: "pending", correlation_id}` challenge response, including resend cooldown, independent of asynchronous delivery success. Unknown extra fields, including capability/role/assignment fields, are rejected with `400 VALIDATION`. Existing provisioned PHONE account login remains supported; PHONE never creates a public account.

Successful ACCOUNT OTP verification consumes the challenge and, under the existing contact advisory lock, atomically creates an ordinary User (`organizerCapable=false`) and encrypted VerifiedContact only if no matching verified email exists. Existing accounts retain their capabilities and assignments. Both paths create a fresh Session and return the same `200 {status: "authenticated", correlation_id}`. ACCOUNT_CREATED and SESSION_CREATED audits commit with those changes. No personal profile/password fields or guest-account conversion are introduced. All existing OTP purpose/context, latest-challenge, delivery, five-minute lifetime, sixty-second cooldown, five-attempt, hashing and consumption rules remain in force.

The account access cookie `eoc_session` retains its fifteen-minute JWT. The separate `eoc_renewal` cookie contains a random 256-bit secret bound to a session and rotation version with a domain-separated MAC. Only a domain-separated keyed hash is persisted. Both account cookies remain HttpOnly, Secure in production, SameSite=None, host-only. Access uses Path=/api/v1; renewal uses Path=/api/v1/auth and expires at the logical session's absolute limit. No credentials are returned in JSON. The DB-backed Session remains authoritative, with an eight-hour sliding idle `expiresAt` bounded by `absoluteExpiresAt` (seven days from creation). Protected activity touches renewable idle expiry at most once a minute with an expiry/revocation guard. Legacy sessions preserve their existing expiry and cannot renew.

`GET /api/v1/auth/account/session` is a safe renewal-cookie CSRF bootstrap after access expiry. A cryptographically authenticated renewal credential and live session are required; it returns only `{csrf_token}`, grants no application access, and does not touch activity or rotate. A historical authentic credential can obtain this token so POST refresh can detect its replay. `POST /api/v1/auth/account/refresh` requires configured Origin and session-bound X-CSRF-Token, validates logical session bounds, locks Session FOR UPDATE, rotates the renewal hash/version, and issues fresh access/renewal cookies. It returns the same authenticated result as verification. Missing/invalid authority is generic `401`; expired/revoked renewal is `401 SESSION_EXPIRED`, CSRF/Origin failures are `403`, and store or critical audit failures are `503 DEPENDENCY_UNAVAILABLE`. All auth responses are private/no-store.

A concurrently presented immediately previous credential within five seconds of rotation receives `409 RENEWAL_CONFLICT` without cookies or new authority. This window never accepts the old credential or extends its lifetime. Older versions or replay after that fixed window atomically revoke the session and erase the renewal hash, audited as SESSION_RENEWAL_REPLAY. Invalid MACs cannot revoke guessed sessions. SESSION_RENEWED audit failure rolls rotation back. Logout accepts valid access or current renewal authority with the same Origin/CSRF checks, revokes the logical session, erases renewal authority and clears both cookies. External session revocation always prevents renewal.

The browser deduplicates renewal in each tab, serializes it with Web Locks where supported, rechecks shared HttpOnly cookies after taking the lock, and broadcasts only auth-state notifications. Browsers without Web Locks use server race handling with bounded retries. Protected reads can recover from a definitive `401 UNAUTHENTICATED`; a mutation is retried at most once only with its existing Idempotency-Key and unchanged request body, CSRF, revision and key. Network failures, uncertain outcomes, forbidden responses and dependency failures never trigger automatic mutation replay. Commands without an idempotency key return `409 AUTH_RENEWED_RETRY_REQUIRED` after renewal for deliberate review/retry. Workspace visibility/access revalidation preserves mounted forms while authority remains valid; expiry, forbidden scope and dependency-unavailable states stay distinct.

**Status:** Slice 2 auth/staff foundation and Slice 3 V2–V6 event management, gate readiness, lifecycle, and configuration-only availability are implemented. V7 implements anonymous PUBLIC discovery and event detail. V8 implements Organizer PRIVATE-link issuance and anonymous bearer detail. V9 implements Organizer standalone PRIVATE-link revoke/reissue with atomic replacement and safe replay; other domain rows remain planned later-slice operations. [API_PLAN.md](API_PLAN.md) and [Phase 1 permissions](../requirements/ROLE_PERMISSION_MATRIX.md) remain authoritative. JSON/HTTPS under versioned `/api/v1`; ISO-8601 UTC timestamps and event IANA zone, opaque IDs, cursor-paged lists. V10 verifies delivered scope against the [implemented Slice 3 OpenAPI representation](SLICE_3_OPENAPI.json); this Markdown remains authoritative and later domain operations remain planned.

## Common command/read semantics

Every protected command authenticates first, authorizes action + event + resource, validates shape/size/state, checks current version when high-impact, then commits facts and audit/publication intent atomically. Never trust browser role, QR contents, client time, or a known ID. Response includes correlation ID and authoritative resource status/revision/time; client timeout means **unknown**, not rejection. Mutation retries use a client idempotency key scoped to actor/action/resource and a request fingerprint where specified; same key/payload returns original outcome, changed payload conflicts. Exact retention windows are deferred. Lists are event-scoped and minimized.

## Final Slice 3 event, discovery, gate and PRIVATE-link contract

The [final approval](../implementation/SLICE_3_FINAL_APPROVAL.md) fixes the technical signature below. **EXISTING** denotes only Slice 2 account/guest proof, session/CSRF, assignment and assigned-gate-scope routes reused here. **PLANNED** denotes an event/discovery/gate operation represented in the older API plan; its exact signature below is **NEW**. These labels record the original contract classification; the status above and IMPLEMENTED V7 labels identify delivered scope. **NEW** operation denotes Organizer-only PRIVATE-link mutation. No Slice 3 product route is EXISTING. All management actions derive owner/assignment from the authenticated account session; query/path IDs never grant authority. `X-CSRF-Token` protects authenticated writes. All write responses carry authoritative event revision and server time; required audit commits with the protected mutation.

The PRIVATE controlled URL under the configured public origin is `/private#access=<opaque-proof>`. The fragment is captured in browser memory, removed from the visible URL, and presented only as the `PrivateLink` authorization header above; it is not an API query/path parameter or persistent browser storage. The server stores a non-reversible protected verifier, not raw proof. At most one link is active per event. There is **no automatic time-based link expiry in MVP**: Organizer revoke/reissue or leaving PRIVATE Published ends authority, and old proof never resurrects. Account/guest verification is separate for later registration ownership. The API must redact proof/URL from logs, audit and errors, disable private response caching and referrers, and use a configured public origin rather than request Host when constructing URLs.

V8 uses the existing `CONTACT_KEY` as a server-only root for purpose-separated HMAC-SHA-256 verifier and AES-256-GCM replay keys (version 1, labels `eoc.private-link.verifier.v1` and `eoc.private-link.replay.v1`). Keep that root stable: changing it invalidates existing proofs and encrypted replay. Access URLs use the configured `FRONTEND_ORIGIN`, never request Host. Local HTTP remains limited to loopback by the existing application configuration; deployed access requires HTTPS transport. V8 introduced no schema change, active-link TTL, or standalone revoke/reissue endpoint. ### Pagination, concurrency, retries and error codes

Both list endpoints use an opaque cursor with optional `cursor`/`limit`, default `limit=20`, maximum `100`, `next_cursor=null` at the end, and no total count. Create Event, create Gate, lifecycle transition, PRIVATE issue/reissue/revoke require `Idempotency-Key` scoped to actor/action/resource plus request fingerprint. Same key/body replays original status/body; changed payload conflicts. Gate, transition and PRIVATE commands also require `If-Match: "<revision>"`; authorized replay is recognized before treating the advanced revision as a new conflict. PATCH requires only `If-Match`, not an idempotency key; on timeout GET/reconcile before a new PATCH. The 24-hour encrypted issuance-response replay window is **not PRIVATE-link expiry**. Active verifier is non-reversible, raw proof is never stored; after replay retention a stale revision blocks accidental second rotation. State change, required audit and one-active constraint commit atomically; audit failure rolls back the mutation. ## Slice 7 finalized versioned snapshot and socket contract

**Status: FINALIZED — VERSIONED UPDATES.** This additive contract supersedes Slice 6's omission of revision/freshness and its snapshot-only transport boundary. All Slice 6 calculations, authorization, privacy, capacity and error semantics remain binding. No forecasting, alerts, volunteers, certificates, checkout/re-entry, corrections, Kafka, camera or offline behavior is added.

All existing fields remain. `as_of` denotes when the coherent committed snapshot was read, not attendance occurrence or transaction commit time. Re-reading the same revision can produce a newer `as_of`, registration count, lifecycle or capacity; those configuration/registration changes do not advance attendance revision. REST is always authoritative.

The dedicated **attendance/operations revision** is the count of committed append-only `AttendanceTransition` rows for this event, calculated in the same SQL statement as occupancy. It is never `Event.revision`, a scan count, registration count, mutable occupancy counter, wall clock, global sequence or second revision mechanism. A new event without attendance starts at 0; an existing event starts at its committed ledger count without reset. Each accepted authoritative attendance transition advances it exactly once when its transaction commits. The current contract supports only CHECK_IN. Rejected/technical attempts, same-scan replay and duplicate scans without state change do not advance it. A rollback publishes neither a new revision nor a successful state notification. Event serialization plus ledger insertion/immutable-history constraints guarantee atomic occupancy/revision and monotonicity under concurrent accepted check-ins, without application read-modify-write or a migration. Future departure/correction operations remain unfinalized; if separately approved they must append accepted transitions and use this same revision, with updated occupancy projection semantics, rather than introduce another sequence.

Socket.IO uses WebSocket transport on `/api/v1/realtime/socket.io` so the existing HttpOnly account cookie path applies. Exact configured frontend Origin is required (including for WebSocket), and the current account token/session is checked at handshake and before each subscription/delivery. No bearer proof in URL/query/auth payload. Organizer ownership with current capability or active EVENT_ADMIN assignment grants the same event-wide authority as REST. Gate/Security, Volunteer, Participant and Guest have no Slice 7 general stream. No generic room-join operation or client-selected role is accepted.

Client emits `operations.subscribe` with exactly `{event_id}` and an acknowledgement callback. One event per connection; a new request clears the previous subscription before validation, including failed replacement. Success acknowledgement: `{ok:true,event_id,revision,as_of}`. Failure: `{ok:false,code}` with safe `UNAUTHENTICATED`, `EVENT_NOT_FOUND`, `VALIDATION` or `DEPENDENCY_UNAVAILABLE`; no event facts. `operations.unsubscribe` clears the subscription. Disconnect clears all subscription state; reconnect requires fresh subscription and REST reconciliation. Revoked/expired account or event authority terminates the socket before further delivery. Authorization is rechecked on every bounded publication pass; dependency failure closes the stream and never fabricates a successful notification.

Server emits `occupancy.updated` with exactly `{message_id,schema_version,event_id,revision,as_of,occurred_at,correlation_id}`. `schema_version=1`; `message_id="operations:" + event_id + ":" + revision` identifies the immutable event revision (stable across redelivery). `revision` uses the dedicated ledger sequence; `as_of` is the committed database read time associated with delivery; `occurred_at` is the latest accepted attendance occurrence, not a fabricated commit timestamp. `correlation_id` identifies the gateway read. Redelivery of the same revision may have a newer read timestamp/correlation. No occupancy values, participant IDs, contact, QR, OTP, credentials or gate identities are broadcast. This is a versioned state-change notification, never authoritative occupancy state.

The existing committed ledger is durable publication intent, persisted with attendance/audit/replay. A single-instance gateway performs bounded serialized passes over active subscriptions (default 1 second, no overlapping pass for a socket), reads the authorized committed snapshot, and emits only after that transaction returns successfully. It coalesces high-rate revisions; skipped intermediate notifications are deliberate detectable gaps. Failed delivery cannot undo attendance; reconnect recovers from REST and the retained ledger. No in-memory scan callback is the only publication intent, no uncommitted transaction emits, and no Kafka/shared broker is introduced. Default Engine.IO liveness is supplemented by authoritative REST confirmation every 30 seconds; this interval is an initial operational setting, not a measured p95/SLA claim. High-scale shared coordination remains outside this single-instance slice.

Notifications received during a fetch raise its required revision; if REST is still behind, retry before labeling live. Initial read, initial successful subscription, reconnect, subscription/context change, gap, schema mismatch, foreground return and the 30-second stale-state check all reconcile through the operations GET. Responses below already confirmed revision are rejected. A connected socket alone never labels data live: only successful subscription plus a current REST reconciliation does. Disconnected/reconnecting/reconciling/failed states are visible with last confirmation time; access loss clears protected values. Event changes remove listeners, unsubscribe/disconnect and abort old reads; old-event messages/responses never populate the new context.

### Closed response schemas

All fields below are required, including fields whose value may be null. Objects reject additional properties. IDs are opaque UUIDs; nonnegative counts/revisions are safe integers. Numeric predictions/intervals/metrics are finite nonnegative numbers and may exceed configured registration capacity. Capacity is an integer >=1 or null for an unconfigured legacy event; it is comparison context only, never a clipping or admission threshold.

`ForecastObserved = {occupied,capacity,attendance_state,revision,as_of}`. This is a minimized Slice 6/7 authoritative operations snapshot: `attendance_state="INSIDE"`; `revision` is the committed per-event attendance-ledger count, never Event.revision; `as_of` is database statement time. It creates no second occupancy authority.

`ForecastCurrent = {event_id,observed,forecast,as_of,correlation_id}`. `observed` is ForecastObserved re-read under current authorization after generation, `forecast` is ForecastRun, and top-level `as_of=observed.as_of` is response snapshot time.

`ForecastHistory = {event_id,observed,items,next_cursor,as_of,correlation_id}`. `observed` and `as_of` have the same meanings; `items` contains ForecastRun values, maximum requested limit, and `next_cursor` is string or null. An event-bound cursor identifies an exclusive `(persisted_at,run_id)` boundary, is at most 512 characters, and must decode to a supported cursor version, the requested event and a valid timestamp/UUID. No retention guarantee or total count is implied.

`ForecastRun = {run_id,event_id,contract_version,status,generated_at,persisted_at,input,method,points,evaluation,limitations,freshness}`:

- `contract_version=1` versions this result schema; `run_id` identifies one immutable persisted attempt, not an attendance/event revision. `event_id` must match the requested event.
- `status` is exactly `AVAILABLE`, `INSUFFICIENT_DATA`, `STALE_INPUT`, `MODEL_UNAVAILABLE`, or `INVALID_INPUT`. It records the generation outcome and is never rewritten when a run ages. Every non-AVAILABLE run has `points:[]` and `evaluation:null`, never invented zero forecasts. A zero is a valid numeric prediction only for an AVAILABLE run grounded in actual observations.
- `generated_at` is the server UTC time at which the attempt produced its result (Node supplies this only for a safe service-failure fallback); `persisted_at` is the database timestamp at which the run was inserted, not a claim of exact commit time.
- `input = {start_at,end_at,last_observation_at,observation_count,revision,occupied,capacity}`. `start_at` is the first included observation timestamp or null if there are none; `end_at` is authoritative extraction `as_of`, also the forecast origin; `last_observation_at` is the last included observation time or null; `observation_count` counts included occupancy observations, not registrations or scan attempts. `revision,occupied,capacity` are the coherent extraction context. `occupied` is observed, not predicted. No observation rows or personal data are public.
- `method = {name,version,baseline_name,baseline_version}`. Strings identify the reproducible method and comparison baseline, not client-selectable algorithms or parameters. The initial `name=baseline_name="persistence"`, `version=baseline_version="1"`: carry forward the last authoritative occupancy for both horizons. This is baseline-only output, not evidence of improvement or production usefulness. Later methods require separate evidence and a reviewed contract change where semantics change.
- `points` is exactly two ForecastPoint objects, ordered `[30,60]`, for AVAILABLE; otherwise it is empty. No extra/partial horizon is valid. `ForecastPoint = {horizon_minutes,target_at,predicted_occupancy,uncertainty}`. `horizon_minutes` is 30 or 60; `target_at=input.end_at + horizon_minutes`, never `generated_at + horizon`. `predicted_occupancy` is the point estimate. `uncertainty = {method,nominal_coverage,lower,upper}`: initial method `validation_residual_quantile`, nominal coverage `0.9`, and an empirical nonnegative ordered interval containing the point estimate. Nominal coverage is a calibration target, not a probability guarantee or measured accuracy; actual held-out coverage is reported separately.
- `evaluation` is null when a forecast cannot be produced, otherwise ForecastEvaluation. It describes **retrospective** chronological evaluation within this run's accepted input window, not future outcomes of its two operational points. `ForecastEvaluation = {kind,split,horizons}` with `kind="BASELINE_ONLY"`, `split={training,validation,test}`, each range `{start_at,end_at}` with chronological nonoverlapping ranges. `horizons` is ordered `[30,60]`; each item is `{horizon_minutes,samples,mae,rmse,baseline_mae,baseline_rmse,interval_coverage,availability_coverage}`. `samples` is a positive integer of evaluable held-out origins with known target outcomes; MAE/RMSE have occupancy-count units. Initial baseline metrics equal method metrics because they are the same method. `interval_coverage` and `availability_coverage` are measured fractions [0,1], never assumed. Availability coverage means evaluated eligible test origins divided by all test origins with a known target. Training/validation/test targets remain inside their respective ranges, so no future target leaks across splits. Validation alone determines the uncertainty interval; test outcomes never fit it. No production acceptance threshold is set.
- `limitations` is an array of safe fixed codes, never arbitrary service prose: initial codes `BASELINE_ONLY`, `CHECK_IN_ONLY`, `EMPIRICAL_UNCERTAINTY`, `NO_PRODUCTION_ACCURACY_CLAIM`. All four occur on every run, including unavailable attempts, to make method/scope limits explicit.
- `freshness = {state,reason,expires_at}` is assessed against the response's authoritative observed context and `as_of`, not immutable generation status. `state` is `CURRENT`, `STALE` or `UNAVAILABLE`. `expires_at=generated_at + 60 seconds` on every run. Rules and reason precedence are below.

All timestamps are ISO-8601 UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, following existing JSON serialization; event schedule retains its existing IANA zone. Partial Draft context does not invent a zone/schedule. There is no separate client clock, predicted commit timestamp or implied attendance change at a sampling timestamp. `input.end_at <= generated_at <= persisted_at <= response.as_of`; timestamp/identity/version/horizon/schema violations from FastAPI become safe INVALID_INPUT attempts rather than disclosed service content.

### Freshness, generation and degraded behavior

For a run whose `status` is not AVAILABLE, `freshness.state="UNAVAILABLE"` and `reason` equals its status, regardless of age. For AVAILABLE, apply this precedence: changed observed attendance revision **or capacity** compared with input gives `STALE/OBSERVATIONS_CHANGED`; otherwise response `as_of >= expires_at` gives `STALE/AGE_EXCEEDED`; otherwise `CURRENT` with `reason:null`. Stale points may be displayed only with their generation time and explicit stale label, never as a current estimate. History recomputes this wrapper at read time; persisted predictions/evaluation do not change. A stale service input uses `status=STALE_INPUT`, has no points and is unavailable, rather than recycling a previous successful run.

The command center requests current once on entering an authorized ready operations context, on explicit forecast refresh, and every 60 seconds while visible; foreground return refreshes it. At most one forecast request per mounted event context is active. Occupancy/socket notifications mark incompatible predictions stale but **never trigger generation**. Forecast timeout/loading/failure does not clear, replace or delay the independent authoritative occupancy view. Event/context change, pagehide or lost operations authority clears forecasts and aborts old requests; late responses cannot populate another event. Age checks may label a retained result stale without a network request.

Each current GET performs fresh extraction, one internal call with a 2,000 ms bounded timeout (including response body), schema/version/horizon/timestamp/plausibility validation, then reauthorization and atomic result persistence. No retry, cache fallback, scheduled job, queue, worker, socket forecast event or public Python endpoint is introduced. MODEL_UNAVAILABLE covers unconfigured/unreachable service, timeout and safe transport failure; INVALID_INPUT covers malformed, unexpected or incompatible service results; INSUFFICIENT_DATA covers inadequate accepted history; STALE_INPUT covers an extraction older than the service's bounded freshness rule. All are `200` with the persisted typed capability result, not HTTP errors. Database/extraction/persistence failures remain `503` with the common `{code,message,correlation_id}` envelope, without a fabricated run. Unknown service error bodies/exception text never pass through. History reads do not need an available Python service.

### Accepted history and reproducible initial policy

Only committed CHECK_IN AttendanceTransition entries joined to active REGISTERED registrations in the same event are authoritative. Rejected/technical/replayed scans and cancellation markers are not observations. Registration count is never an occupancy proxy. Current CHECK_IN-only semantics imply no departure; accepted history and the end snapshot establish exact occupancy between transitions, not invented attendance. Observation timestamps use server ledger/extraction times; client `observed_at` never sets them. No state is assumed before the earliest retained accepted transition.

The initial bounded input window is the last six hours ending at extraction `as_of`, shortened to the earliest authoritative transition if later. Observations are exact reconstructed occupancy at successive one-minute boundaries within that window, plus the extraction endpoint if not already a boundary; no interpolation of hypothetical arrivals. Maximum 361 points and no pre-first-transition zero padding. The last endpoint is a fresh authoritative observation even if no check-in happened recently: quiet attendance is not stale data. Input age greater than 60 seconds, future/unsorted/duplicate timestamps, negative/decreasing CHECK_IN occupancy, mismatched final context or unsupported versions are rejected or marked stale safely. At least 270 one-minute observations are required, giving three chronological blocks of at least 90 observations; the 60-minute horizon leaves at least 30 evaluable origins per block. Sparse or newly started events return INSUFFICIENT_DATA, never synthetic training history.

The method uses the latest observed count as its deterministic 30/60-minute persistence baseline. Within each chronological third, only origins whose targets remain in that third are evaluated; available actual observations define targets. A horizon-specific 90th percentile of absolute validation residuals (deterministic nearest-rank rule) supplies a symmetric interval around the point, lower-clipped at zero. Chronological held-out test MAE/RMSE, comparison-baseline metrics, empirical interval coverage and availability coverage accompany an AVAILABLE run. These initial bounds establish reproducible, bounded work and transparent sparse-data behavior, not measured latency/accuracy acceptance. No training serialization or unnecessary ML algorithm/dependency is required for persistence. Reproducible run/window/revision/method metadata and immutable accepted facts support later evaluation; retention and production acceptance thresholds remain deferred.

| PATCH same task path + `/status` | V only; `{status}`; If-Match | 200 `{task,correlation_id}`, ETag | 403 FORBIDDEN for staff impersonation; 409 VERSION_CONFLICT/INVALID_TRANSITION; VOLUNTEER_TASK_STATUS_CHANGED |

| GET `/events/{eventId}/results` | M; no query/body; COMPLETED only | 200 `{results,correlation_id}` | 409 RESULTS_NOT_COMPLETED after authorization; EVENT_RESULTS_VIEWED before returning |

Task list order is `created_at DESC,id DESC`, default 25/max 100, no total. Manager list includes persisted terminal task history in that event; own list exposes only current task/grant binding and excludes CANCELLED before pagination. Detail read does not extend task/role authority. No task deletion, reset, restart or general task-history endpoint; existing task detail and restricted audit search provide history.

### Completed results and coherent authority

Results is a closed object with `event_id,event_state:COMPLETED,total_registrations,cancelled_registrations,accepted_check_ins,attendance_rate_percentage,gate_check_ins,certificate_eligible_count,certificate_issued_count,certificate_revoked_count,certificate_delivery_counts,data_limitations,as_of`. All counts are nonnegative safe integers. Gate entries are exactly `{gate_id,accepted_check_ins}`, ordered gate_id ascending and include zero-count configured gates. Delivery counts are exactly `{NOT_REQUIRED,PENDING,SENDING,SENT,UNKNOWN,FAILED}`. No participant/contact/name data is returned.

- Total/cancelled registration counts count persisted registration **rows**, including retained cancellation/reregistration history, not distinct humans. Accepted check-ins count the bound CHECK_IN ledger, never ScanDecision attempts/replays or the registration marker alone.
- Attendance denominator is `total_registrations - cancelled_registrations` (current REGISTERED population). Rate is accepted_check_ins / denominator × 100, rounded to two decimal places, only if denominator is positive and the bound accepted population is valid. Otherwise rate is null; never divide by total historical rows or fabricate a denominator.
- Certificate eligible count is the current **ELIGIBLE status** used by Slice 9: REGISTERED row, matching accepted ledger evidence and immutable firstAcceptedCheckInAt, and no persisted issued/revoked Certificate. Recipient-name presence is not eligibility. Issued/revoked counts count distinct Certificate rows by their current ISSUED/REVOKED status. These counts are mutually exclusive; revoked is not also counted as currently issued.
- Delivery counts count distinct CertificateDelivery rows bound to the event/certificate, including revoked certificates whose authorized SENDING attempt subsequently completes. Absence of a legacy delivery row is not NOT_REQUIRED. Never sum batch items/attempts into event-wide certificate/delivery counts.
- Acquire current manager authority in the existing event/session/assignment lock order, then calculate all metrics, persisted work limitations and `statement_timestamp()` in **one PostgreSQL statement snapshot**. event_state and all facts refer to that statement; as_of is its UTC timestamp, not a browser time or last update. Completed does not freeze certificate issuance/delivery; subsequent reads may change. No materialized analytics table, historical occupancy series or background analytics job.

data_limitations is an array of distinct stable codes, sorted lexically: always `NO_EXIT_OR_DWELL_DATA` and `HISTORICAL_OCCUPANCY_NOT_RECORDED`; add `NO_REGISTERED_DENOMINATOR` if zero, `ATTENDANCE_RATE_UNAVAILABLE` for invalid accepted/denominator evidence, `CERTIFICATE_PROCESSING_INCOMPLETE` if retained issue work/batch processing is pending/running, `DELIVERY_PENDING_OR_UNCERTAIN` if delivery is PENDING/SENDING/UNKNOWN, and `DELIVERY_STATE_NOT_RECORDED` when a persisted certificate lacks a delivery row. The UI explains these codes with fixed text. Same-event gate facts only; no historical benchmarking, cross-event ranking/comparison or predictive metrics. This deliberately leaves richer FR-ANL-002 comparisons for their later owning scope.

### Audit query, minimized evidence and pagination

Exact optional query parameters: `actor` (account UUID, or literal SYSTEM/GUEST), `action` (exact uppercase action identifier, 1–80), `target_type` (enum below), `outcome` (exact uppercase identifier, 1–24), `from` (inclusive UTC), `to` (exclusive UTC), `cursor`, `limit` (integer 1–100/default 25). Action/outcome syntax is `[A-Z][A-Z0-9_]*`; no substring/full-text/contact search. UUID actor filters actorUserId, SYSTEM/GUEST filter actorKind. Omitted filters are unrestricted only **inside the currently authorized event**. If both times exist require from < to. Filters apply before keyset pagination; action/outcome with no matching records return an empty page, not an enumeration API.

AuditEvent DTO is exactly `id,event_id,actor:{kind:ACCOUNT|GUEST|SYSTEM,id:UUID|null},action,target_type,target_id,outcome,occurred_at,correlation_id`. occurred_at maps to existing createdAt. actor.id maps only existing actorUserId; never synthesize a historical role from current assignments, expose a guest contact/hash, or attach names/emails. target_type is EVENT/GATE/USER/REGISTRATION/CREDENTIAL/SCAN_DECISION/PRIVATE_ACCESS_LINK/CERTIFICATE/CERTIFICATE_ISSUE_WORK/CERTIFICATE_BATCH/CERTIFICATE_DELIVERY/VOLUNTEER_TASK/UNKNOWN. target_id is nullable UUID; UNKNOWN must have null target_id. No raw metadata is serialized.

Target extraction is action-family allowlisted, with UUID type checks, before pagination/filtering. EVENT_CREATED/UPDATED/TRANSITIONED and Slice 11 AUDIT_SEARCHED/EVENT_RESULTS_VIEWED target their stored eventId. GATE_CREATED uses gate_id; STAFF_GRANTED/REVOKED use targetUserId (USER); successful PRIVATE_LINK actions use link_id; REGISTRATION_CREATED/CANCELLED/VIEWED and certificate name/status actions use registration_id; CREDENTIAL_VIEWED uses credential_id; SCAN_CHECK_IN uses scan_decision_id; CERTIFICATE_ARTIFACT_VIEWED/REVOKED use certificate_id; issue-work actions use issue_work_id; CERTIFICATE_BATCH_* use batch_id; CERTIFICATE_DELIVERY_* use delivery_id; VOLUNTEER_TASK_* use task_id. Fields come only from the known writer/action mapping, not arbitrary metadata keys. Missing/invalid/unrecognized legacy targets are UNKNOWN/null. No audit backfill/update, no exposure of reasons/free text/ciphertext/provider diagnostics. Predicate and DTO must use the identical target mapping. Denial events lacking a safely persisted target remain UNKNOWN.

Audit order is `occurred_at DESC,id DESC`; default 25/max 100. Task/audit cursors are opaque URL-safe `base64url(JSON).base64url(HMAC-SHA256)` tokens, maximum 2048 characters. The closed internal payload is `{v:1,resource:TASKS|AUDIT,actor_id:UUID,event_id:UUID,filter_hash:64-lowercase-hex,last_at:UTC,last_id:UUID}`. Sign the encoded payload prefixed with `slice11:tasks:v1:` or `slice11:audit:v1:` using the existing contact/cursor key and existing HMAC/timing-safe verification pattern. filter_hash is the existing canonical JSON request fingerprint of normalized filters/view (omitted optional filters represented as null; UUIDs lowercase); cursor/limit are excluded. last_at is task created_at or audit occurred_at. Verify signature/closed shape/scope on every request; changed filters/view/event/actor or forged cursor is `400 VALIDATION`. Use strict tuple-less-than last key and return next_cursor only if limit+1 proves another row. Lists are live keyset reads, not a frozen historical snapshot. Newer inserts, including the search's own audit event, do not cause duplicates or a self-extending next-page loop. Reauthorize every page; never paginate an unscoped fetch then redact/filter in application memory.

Query authorized rows and insert AUDIT_SEARCHED in the same transaction; commit the required record before serializing/returning data. Search sees committed evidence before its own record; later searches may see it. Record actor/event/action/outcome/correlation, controlled canonical filters and result count, but no cursor, task instructions, contact or raw returned records. If audit insert or commit fails, return `503 DEPENDENCY_UNAVAILABLE` with no audit data. No update/delete/export behavior. EVENT_RESULTS_VIEWED also commits before results are returned. Task writes, their evidence and completed command replay commit atomically; mandatory audit failure rolls back the mutation. Authorized replay emits no duplicate domain-change audit. Denied privileged requests use existing safe denial audit/fail-closed conventions.

### Minimal planned persistence and concurrent commands

One VolunteerTask concept is sufficient: UUID id, immutable eventId FK, assignedVolunteerId FK and specific volunteerRoleAssignmentId binding; title/instructions/location/times above; four-value status; createdAt/updatedAt; internal positive integer revision (initial 1); nullable cancelledAt, cancelledByUserId (User FK) and cancellationReason. FKs restrict destructive removal. Enforce nonblank/bounded text, valid time range, positive revision, allowed status edges and immutable event/creation identity.
