## Common command/read semantics

Every protected command authenticates first, authorizes action + event + resource, validates shape/size/state, checks current version when high-impact, then commits facts and audit/publication intent atomically. Never trust browser role, QR contents, client time, or a known ID. Response includes correlation ID and authoritative resource status/revision/time; client timeout means **unknown**, not rejection. Mutation retries use a client idempotency key scoped to actor/action/resource and a request fingerprint where specified; same key/payload returns original outcome, changed payload conflicts. Exact retention windows are deferred. Lists are event-scoped and minimized.

## Final Slice 3 event, discovery, gate and PRIVATE-link contract

The [final approval](../implementation/SLICE_3_FINAL_APPROVAL.md) fixes the technical signature below. **EXISTING** denotes only Slice 2 account/guest proof, session/CSRF, assignment and assigned-gate-scope routes reused here. **PLANNED** denotes an event/discovery/gate operation represented in the older API plan; its exact signature below is **NEW**. These labels record the original contract classification; the status above and IMPLEMENTED V7 labels identify delivered scope. **NEW** operation denotes Organizer-only PRIVATE-link mutation. No Slice 3 product route is EXISTING. All management actions derive owner/assignment from the authenticated account session; query/path IDs never grant authority. `X-CSRF-Token` protects authenticated writes. All write responses carry authoritative event revision and server time; required audit commits with the protected mutation.

### Field, payload and availability schemas

Organizer PATCH allowlist: `name`, `description`, `public_location`, `image_url`, `category`, `tags[]`, `start_at`, `end_at`, `time_zone`, `visibility` (`PUBLIC`/`PRIVATE`), `registration_capacity`, `registration_opens_at`, `registration_closes_at`, `registration_cancellation_cutoff_at`, `registration_manually_closed`, `checkout_enabled`. Assigned Admin PATCH allowlist is **only** `name`, `description`, `public_location`, `image_url`, `category`, `tags[]`; reject any other submitted field rather than ignoring it. Only submitted fields change; null clears optional fields. Validate nonblank name, ordered schedule, valid IANA zone, positive single registration cap, coherent registration times and optional public HTTPS image reference. Organizer policy/configuration changes are Draft/Published-only in Slice 3. No editable certificate eligibility rule, unrestricted Live PATCH, image-upload endpoint, or client-supplied owner/state. An Organizer PRIVATE-to-PUBLIC edit atomically invalidates the active proof so it cannot later revive.

The PRIVATE controlled URL under the configured public origin is `/private#access=<opaque-proof>`. The fragment is captured in browser memory, removed from the visible URL, and presented only as the `PrivateLink` authorization header above; it is not an API query/path parameter or persistent browser storage. The server stores a non-reversible protected verifier, not raw proof. At most one link is active per event. There is **no automatic time-based link expiry in MVP**: Organizer revoke/reissue or leaving PRIVATE Published ends authority, and old proof never resurrects. Account/guest verification is separate for later registration ownership. The API must redact proof/URL from logs, audit and errors, disable private response caching and referrers, and use a configured public origin rather than request Host when constructing URLs.

V8 uses the existing `CONTACT_KEY` as a server-only root for purpose-separated HMAC-SHA-256 verifier and AES-256-GCM replay keys (version 1, labels `eoc.private-link.verifier.v1` and `eoc.private-link.replay.v1`). Keep that root stable: changing it invalidates existing proofs and encrypted replay. Access URLs use the configured `FRONTEND_ORIGIN`, never request Host. Local HTTP remains limited to loopback by the existing application configuration; deployed access requires HTTPS transport. V8 introduced no schema change, active-link TTL, or standalone revoke/reissue endpoint. V9 reuses the persistence foundation for standalone revoke/reissue; reissue results use the same encrypted 24-hour replay window, while secret-free revoke results use ordinary command replay retention.

### Pagination, concurrency, retries and error codes

Both list endpoints use an opaque cursor with optional `cursor`/`limit`, default `limit=20`, maximum `100`, `next_cursor=null` at the end, and no total count. Management order: `created_at DESC,event_id DESC`; PUBLIC order: `published_at DESC,event_id DESC`. Cursor binds sort and query scope; authorization and PUBLIC+Published filter precede pagination. It is not a historical snapshot.

Create Event, create Gate, lifecycle transition, PRIVATE issue/reissue/revoke require `Idempotency-Key` scoped to actor/action/resource plus request fingerprint. Same key/body replays original status/body; changed payload conflicts. Gate, transition and PRIVATE commands also require `If-Match: "<revision>"`; authorized replay is recognized before treating the advanced revision as a new conflict. PATCH requires only `If-Match`, not an idempotency key; on timeout GET/reconcile before a new PATCH. The 24-hour encrypted issuance-response replay window is **not PRIVATE-link expiry**. Active verifier is non-reversible, raw proof is never stored; after replay retention a stale revision blocks accidental second rotation. State change, required audit and one-active constraint commit atomically; audit failure rolls back the mutation. Timeout is an unknown outcome: retry a POST only with the same key/body/precondition, or reconcile from authorized status. Do not return an active URL from management GET.

| --- | --- |
| `400 VALIDATION` | Malformed JSON/query/header, unsupported field/type/range, invalid time/zone/cursor/limit. |

| `403 FORBIDDEN`, `403 CSRF_INVALID` | Wrong role/action/field or failed authenticated-write CSRF check. |

The common envelope remains `{code,message,correlation_id,details?,retryable?}` with safe field details only. `429` remains generic abuse throttling, not a proof-validity oracle. PRIVATE failure has no public per-cause code. Generic `503` reveals no protected event fact.

### Lifecycle and role boundary

Organizer alone performs Draft→Published, Published→Live, Live→Completed and Draft/Published/Live→Cancelled under [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md); cancellation requires confirmation and nonblank reason in this Slice 3 command. Publish and Live each independently require at least one persistent authorized Event–Gate association (`UC-02`, `FR-EVT-002`, `FR-EVT-004`). Partial Drafts are savable; no clock-driven event transition or terminal reopening. Event Admin may configure an assigned Draft/Published Gate and edit only its approved fields; Event Admin never transitions, cancels, changes capacity/visibility/schedule/registration policy, or mutates PRIVATE link. Gate/Security, Volunteer, Participant, Guest and anonymous visitors have no management route authority. Anyone with a valid PRIVATE proof can see only the public-allowlisted PRIVATE Published detail. No registration, QR, scan/check-in, occupancy, forecast, alert, certificate or volunteer workflow route is introduced by this Slice 3 contract.

## Error envelope and HTTP categories

Error body: `{ code, message, correlation_id, details?, retryable? }`; field details only for safe validation. The stable Slice 3 catalog is specified above: PRIVATE bearer failures collapse to `404 PRIVATE_UNAVAILABLE`, while protected management without a valid account session is `401 UNAUTHENTICATED`. Later-slice exact codes are finalized with their OpenAPI contracts. Generic categories remain `400` malformed/validation, `403` forbidden, `404` safe not found, `409` duplicate/invalid transition/version/idempotency conflict, `422` distinguishable policy-invalid, `429` throttled, and `503` dependency unavailable. Clients distinguish policy rejection from technical/unknown outcome. No stack traces, raw QR, OTP, account credentials, contact data in gate responses, or internal identifiers that leak private resources.

`registration` contains exactly `registration_id,event_id,state,relationship,created_at,cancelled_at,event_state,cancellation_cutoff_at`. States are REGISTERED/CANCELLED; current request relationship is `own` or `managed` without exposing owner identity. The participant UI offers QR/self-cancellation only for own records. The self-cancellation cutoff defaults to event start. Event cancellation leaves registration rows unchanged. The future first-accepted-check-in fact is a cancellation guard only; this slice has no scanner/check-in route.

New registration requires PUBLISHED independently of the unchanged five-field configuration-only availability object. Opening, effective closing (configured closing or event start) and manual closure are checked at command time. `409 REGISTRATION_NOT_OPEN`, `REGISTRATION_CLOSED`, `EVENT_CANCELLED`, `DUPLICATE_ACTIVE`, `CAPACITY_FULL`, `CANCELLATION_CUTOFF_REACHED` and `ALREADY_CHECKED_IN` describe authorized registration decisions. Capacity counts only REGISTERED rows; cancellation releases a place, but cannot bypass time/manual/lifecycle closure. No occupancy or participant counts enter discovery.

Guest identity is the existing contact-type-separated normalized HMAC subject, persisted as a GuestIdentity without an account or raw contact. Guest self proof expires after the existing 15 minutes; `/auth/guest/self` additionally supplies its CSRF token. Writes require the configured frontend Origin and matching account-session or guest-proof CSRF. When both cookies exist, account identity takes precedence; renew/sign out the account to use a different guest identity. `403 FRESH_GUEST_PROOF_REQUIRED` requires guest reverification before cancellation. All proof purposes/event bindings and current account/session/staff authority are checked under the event lock, including before command replay.

Commands retain ordinary secret-free replay for seven days, scoped to account or guest identity/action/resource/key. Same-key retries return the original result without issuing another credential or restoring cancelled state. Recover current state with GET after an unknown result or replay. These participant commands do not mutate event configuration/revision and do not require If-Match. Re-registration uses a new command key, registration ID and QR token. There is no standalone credential reissue/revoke API in this slice.

Registration and cancellation use existing PostgreSQL READ COMMITTED event serialization and conditional active identity uniqueness. Required mutation, credential change, successful audit and replay result commit atomically. Scoped registration/credential reads and denials are audited without contact hashes, QR tokens or bearer proofs; audit/database failures return generic `503 DEPENDENCY_UNAVAILABLE`. Credential and registration responses use private/no-store and no-referrer headers. Unknown/unowned registrations have no ownership details in their errors. PRIVATE registration attempts without valid discovery authority cannot reveal protected event existence.

QR tokens use 256 random bits with a version prefix, HMAC-SHA-256 verifiers and a registration-bound AES-256-GCM owner representation. Purpose-separated version-1 keys derive from the existing server-only CONTACT_KEY; keep it stable. Raw tokens do not enter database JSON, command replay, logs, audit, URLs or browser persistence. Cancellation destroys the encrypted owner representation and revokes its verifier in the same transaction. The nullable persisted expiration is enforced if present; no automatic QR lifetime is invented while the documented lifetime policy remains TBD. Retrieval proves ownership, not admission; later scanning must independently check current credential, registration and event eligibility. Public/private event-detail routes never expose registration data.


## Slice 5 implemented scanner and check-in contract

The additive [Slice 5 OpenAPI](SLICE_5_OPENAPI.json) implements exactly `POST /api/v1/scan-decisions`. Slice 3's twelve and Slice 4's five operations are preserved. This operation is fixed to CHECK_IN; it has no checkout/re-entry direction, correction, occupancy, camera, offline or live publication workflow.

Account session, configured frontend Origin, X-CSRF-Token and Idempotency-Key are required. The strict request contains exactly `scan_id,event_id,gate_id,credential`; identifiers are UUIDs, scan_id is canonical lowercase and Idempotency-Key must equal it. Credential is a nonempty string of at most 128 characters, transported only in the POST body. Unknown fields, client role/identity/registration fields, direction, query parameters and invalid identifiers receive `400 VALIDATION`. An invalid opaque-token format within an otherwise valid request is a credential rejection, not a request-shape error. No If-Match is required: scans do not edit event configuration/revision.

Only a current GATE_SECURITY assignment to the supplied event/gate permits execution. The gate must belong to that event. Organizer or Event Admin authority alone permits no scan execution; separately assigned Gate/Security authority is independent. Anonymous, guest-proof-only, Participant and Volunteer actors cannot scan. Missing/foreign/unassigned event or gate produce the same `403 UNAUTHORIZED_GATE`, without revealing protected existence. Current session/user and exact gate assignment are locked before processing and before replay.

`200` contains exactly `scan_id,event_id,gate_id,decision,reason,registration_status,attendance_status,decided_at,replayed,correlation_id`. Decision is ACCEPTED or REJECTED; reasons are ACCEPTED, INVALID_CREDENTIAL, EXPIRED_CREDENTIAL, CANCELLED_CREDENTIAL, ALREADY_CHECKED_IN or REGISTRATION_UNAVAILABLE. Unknown, forged, malformed and wrong-event credentials all use INVALID_CREDENTIAL with null registration/attendance status: a distinct WRONG_EVENT response would reveal that an arbitrary proof belongs elsewhere. Credential lookup is restricted to the authorized event. Known event-scoped credentials expose only REGISTERED/CANCELLED and NOT_ARRIVED/INSIDE status. No registration/credential IDs, verifiers, QR proof, participant contact, ownership or management data are returned. Display names are not fabricated because the existing identity model has no display-name field.

Admission requires LIVE, a current REGISTERED registration and an active version-1 Slice 4 credential verifier. Persisted expiration is enforced when present; no TTL is invented. Revoked/cancelled credentials are rejected. Lifecycle is independent of the unchanged configuration-only registration availability object, which is neither changed nor consulted for gate admission. A first accepted scan appends one CHECK_IN transition, moving NOT_ARRIVED to INSIDE. Later different-ID attempts are durable ALREADY_CHECKED_IN rejections. Event cancellation/terminal states prevent new check-ins without rewriting registration or attendance history. Slice 4's firstAcceptedCheckInAt barrier is set by ledger insertion and prevents cancellation by every role after check-in.

Existing CommandReplay provides seven-day secret-free replay scoped to account/SCAN_CHECK_IN/gate/scan_id. The fingerprint includes event/gate/scan_id and a purpose-separated keyed credential fingerprint, never raw proof. Same-ID/same-request delivery returns the original decision and time with replayed=true and current correlation_id; it creates no second logical attempt, transition or audit. Changed fingerprint receives `409 IDEMPOTENCY_CONFLICT` after current authorization. After replay expiry, the retained scan ID receives `410 SCAN_REPLAY_EXPIRED`; it is not reconstructed from the ledger or reused for a new attempt. Use a new scan ID deliberately after holding entry. A genuine fresh scan uses a new ID, even for the same QR.

The event row is locked FOR UPDATE at READ COMMITTED; session/user/assignment/gate locks hold current authority through commit. Accepted/rejected logical decisions retain server time, event, gate, operator, authorized credential/registration reference where known, decision/reason and correlation. Unknown/wrong-event proof retains no foreign reference. Each new decision, accepted transition, cancellation barrier, required audit and replay result commit atomically. PostgreSQL unique constraints prevent duplicate accepted check-in and duplicate logical attempts; composite foreign keys preserve associations, matching-source/deferred triggers enforce accepted decision/ledger correspondence, and scan/attendance history is append-only. Pre-decision authentication, CSRF, malformed or scope denials are audited with safe codes and validated requested context where available; they create no attendance. Critical audit/database failure returns `503 DEPENDENCY_UNAVAILABLE` and rolls back state. A technical/unknown result always holds entry; retry the same command instead of treating it as a policy rejection.

Responses use private/no-store and no-referrer. The `/scanner` UI uses only current Gate/Security assignments and verifies gate context through the existing scoped route. It clears the masked token input on submission, retains an unknown command only in memory for exact retry, and drops it on completion, pagehide, unmount or scope loss. It supports Light/Dark/System, accepted/rejected/duplicate states, loading, scope loss and deliberate recovery. It adds no participant registration action or participant lookup.

## Slice 6 implemented attendance and occupancy snapshot

The additive [SLICE_6_OPENAPI.json](SLICE_6_OPENAPI.json) implements only `GET /api/v1/events/{eventId}/operations` under the already planned operations prefix. Frozen Slice 3–5 operation artifacts and discovery allowlists remain unchanged. This is an internal read-only snapshot, not a registration action or scanner admission decision.

Current Organizer authority on an owned event or an active EVENT_ADMIN assignment is required. Gate/Security retains only its existing exact-gate scanner scope; that role alone, Volunteer, Participant, Guest and anonymous callers receive no event-wide occupancy authority. Account authentication is required. Unknown, malformed and out-of-scope event IDs share `404 EVENT_NOT_FOUND`. No query/body fields are accepted (`400 VALIDATION`). Session loss returns `401 UNAUTHENTICATED`; database or required denial-audit failure returns `503 DEPENDENCY_UNAVAILABLE`. Reads use private/no-store and no-referrer responses. Successful reads do not create audit noise; protected denials are audited without event facts or participant data. As a GET, this route requires no CSRF mutation token, revision precondition, idempotency key or replay behavior; Slice 7 adds response revision/freshness as finalized below.

Slice 6 response allowlist (extended by required `revision,as_of` in Slice 7 below): `{event_id,event_name,event_state,occupied,registered,capacity,remaining,utilization_percentage,attendance_state,last_attendance_at,calculated_at,correlation_id}`. `attendance_state` is `INSIDE`. `registered` counts active REGISTERED records separately from attendance. `occupied` counts those registrations' authoritative committed CHECK_IN ledger transitions; the first-check-in cancellation marker alone does not establish occupancy. Slice 5 has exactly one CHECK_IN per registration and no departure transition. Terminal lifecycle changes do not erase attendance. `last_attendance_at` is the latest included accepted check-in, or null; `calculated_at` is database statement time, not a claim that attendance just changed.

**Capacity remains the configured registration cap, never a physical gate-entry ceiling.** `remaining = capacity - occupied`; `utilization_percentage = occupied / capacity * 100`, rounded to two decimal places. Negative remaining and utilization above 100 are valid: occupied 2 with capacity 1 yields remaining -1 and utilization 200. Neither these calculations nor their UI block valid registered check-ins, cancel registrations or forbid an otherwise permitted capacity reduction. Null legacy Draft capacity produces null remaining/utilization instead of an invented limit. The configuration-only availability object and all registration semantics remain unchanged.

The read reuses the established event → current session/user → management-assignment lock order and computes event configuration, active registrations, attendance count and timestamps in one SQL statement. It observes committed attendance coherently with configuration, waiting for an existing in-flight event transaction when needed. This brief read serialization introduces no capacity admission check. Existing scanner uniqueness, replay and atomic attendance/audit guarantees are unchanged. No occupancy counter, materialized projection or schema migration is added.

The Slice 6 frontend established the manager-context operations link and `/operations/{eventId}` with manual refresh, calculated freshness, lifecycle, zero/unconfigured/above-capacity states, and safe loading/retry/session/scope-loss handling. Slice 7 extends this view as finalized below. Light/Dark/System themes and the deferred correction boundary remain unchanged.

## Slice 7 finalized versioned snapshot and socket contract

**Status: FINALIZED — VERSIONED UPDATES.** This additive contract supersedes Slice 6's omission of revision/freshness and its snapshot-only transport boundary. All Slice 6 calculations, authorization, privacy, capacity and error semantics remain binding. No forecasting, alerts, volunteers, certificates, checkout/re-entry, corrections, Kafka, camera or offline behavior is added.

`GET /api/v1/events/{eventId}/operations` adds required `revision` (nonnegative safe integer) and `as_of` (ISO-8601 UTC database statement timestamp, equal to `calculated_at`). All existing fields remain. `as_of` denotes when the coherent committed snapshot was read, not attendance occurrence or transaction commit time. Re-reading the same revision can produce a newer `as_of`, registration count, lifecycle or capacity; those configuration/registration changes do not advance attendance revision. REST is always authoritative.

The dedicated **attendance/operations revision** is the count of committed append-only `AttendanceTransition` rows for this event, calculated in the same SQL statement as occupancy. It is never `Event.revision`, a scan count, registration count, mutable occupancy counter, wall clock, global sequence or second revision mechanism. A new event without attendance starts at 0; an existing event starts at its committed ledger count without reset. Each accepted authoritative attendance transition advances it exactly once when its transaction commits. The current contract supports only CHECK_IN. Rejected/technical attempts, same-scan replay and duplicate scans without state change do not advance it. A rollback publishes neither a new revision nor a successful state notification. Event serialization plus ledger insertion/immutable-history constraints guarantee atomic occupancy/revision and monotonicity under concurrent accepted check-ins, without application read-modify-write or a migration. Future departure/correction operations remain unfinalized; if separately approved they must append accepted transitions and use this same revision, with updated occupancy projection semantics, rather than introduce another sequence.

Socket.IO uses WebSocket transport on `/api/v1/realtime/socket.io` so the existing HttpOnly account cookie path applies. Exact configured frontend Origin is required (including for WebSocket), and the current account token/session is checked at handshake and before each subscription/delivery. No bearer proof in URL/query/auth payload. Organizer ownership with current capability or active EVENT_ADMIN assignment grants the same event-wide authority as REST. Gate/Security, Volunteer, Participant and Guest have no Slice 7 general stream. No generic room-join operation or client-selected role is accepted.

Client emits `operations.subscribe` with exactly `{event_id}` and an acknowledgement callback. One event per connection; a new request clears the previous subscription before validation, including failed replacement. Success acknowledgement: `{ok:true,event_id,revision,as_of}`. Failure: `{ok:false,code}` with safe `UNAUTHENTICATED`, `EVENT_NOT_FOUND`, `VALIDATION` or `DEPENDENCY_UNAVAILABLE`; no event facts. `operations.unsubscribe` clears the subscription. Disconnect clears all subscription state; reconnect requires fresh subscription and REST reconciliation. Revoked/expired account or event authority terminates the socket before further delivery. Authorization is rechecked on every bounded publication pass; dependency failure closes the stream and never fabricates a successful notification.

Server emits `occupancy.updated` with exactly `{message_id,schema_version,event_id,revision,as_of,occurred_at,correlation_id}`. `schema_version=1`; `message_id="operations:" + event_id + ":" + revision` identifies the immutable event revision (stable across redelivery). `revision` uses the dedicated ledger sequence; `as_of` is the committed database read time associated with delivery; `occurred_at` is the latest accepted attendance occurrence, not a fabricated commit timestamp. `correlation_id` identifies the gateway read. Redelivery of the same revision may have a newer read timestamp/correlation. No occupancy values, participant IDs, contact, QR, OTP, credentials or gate identities are broadcast. This is a versioned state-change notification, never authoritative occupancy state.

The existing committed ledger is durable publication intent, persisted with attendance/audit/replay. A single-instance gateway performs bounded serialized passes over active subscriptions (default 1 second, no overlapping pass for a socket), reads the authorized committed snapshot, and emits only after that transaction returns successfully. It coalesces high-rate revisions; skipped intermediate notifications are deliberate detectable gaps. Failed delivery cannot undo attendance; reconnect recovers from REST and the retained ledger. No in-memory scan callback is the only publication intent, no uncommitted transaction emits, and no Kafka/shared broker is introduced. Default Engine.IO liveness is supplemented by authoritative REST confirmation every 30 seconds; this interval is an initial operational setting, not a measured p95/SLA claim. High-scale shared coordination remains outside this single-instance slice.

Client stores only confirmed REST revision N. Incoming N+1 marks reconciling and fetches REST; >N+1 marks a revision gap and fetches REST; <=N is ignored and cannot regress display. Notifications received during a fetch raise its required revision; if REST is still behind, retry before labeling live. Initial read, initial successful subscription, reconnect, subscription/context change, gap, schema mismatch, foreground return and the 30-second stale-state check all reconcile through the operations GET. Responses below already confirmed revision are rejected. A connected socket alone never labels data live: only successful subscription plus a current REST reconciliation does. Disconnected/reconnecting/reconciling/failed states are visible with last confirmation time; access loss clears protected values. Event changes remove listeners, unsubscribe/disconnect and abort old reads; old-event messages/responses never populate the new context.
