# Phase 2 Authentication and RBAC Architecture

**Status:** architecture contract; the Slice 2 identity/RBAC foundation exists, while the approved Slice 3 event and PRIVATE-link contract below remains to be implemented. [ROLE_PERMISSION_MATRIX.md](../requirements/ROLE_PERMISSION_MATRIX.md) is the permission source of truth; this specifies enforcement. Slice 2's approved plan and implementation govern its session/OTP mechanism; the finalized Slice 3 API/security details are in [API_CONTRACT.md](../api/API_CONTRACT.md).

Authentication establishes an actor: verified account session for Participant/Organizer/Event Admin/Gate/Volunteer, or a short-lived OTP-verified guest ownership context for registration access/recovery/cancellation. OTP must prove the particular verified email/phone and be bounded by expiry, replay and abuse controls; guest needs no permanent account. Roles alone do not grant access: authorization evaluates actor, action, event, assignment/gate, resource owner, lifecycle and current registration/attendance state on every API command/read and Socket.IO subscription. Server-derived identity only; client-supplied role/event context is untrusted. Revoke assignment/session access on next request and disconnect/revalidate live channel.

| Actor | Allowed scope | Explicit exclusions |
| --- | --- | --- |
| Organizer | Own event creation, lifecycle including Live cancellation, registration opening/closing-time configuration and manual close/reopen, Event Admin grants; permitted event operations, alerts, reasoned corrections, certificates/retry, restricted audit. | No post-check-in registration cancellation, unrestricted export or direct staff credential control. |
| Event Admin | Assigned-event Draft/Published edits to name, description, public venue/location, image/banner, public category/tags; gates/staff/volunteer assignments within grant, pre-check-in registration cancellation, correction, alerts, explicit certificate actions/retry, restricted audit. | No ownership transfer, Admin promotion/grant, lifecycle transition/event cancellation, capacity, visibility, schedule/time zone, cancellation cutoff, registration opening/closing-time configuration, manual close/reopen, attendance/certificate policy, other unlisted event edits, or unrestricted Live event-detail edit. |
| Gate/Security | Assigned event **and gate** scan/result/history and assigned-gate operational alerts read-only; result identity allowlist: display name, registration status, relevant attendance status, event context, scan result. | No email/phone/OTP/credentials, other-gate history, correction, alert action, event configuration or manual override. |
| Volunteer | Own bounded assignment/instructions/applicable time/location and own ASSIGNED → IN_PROGRESS → COMPLETED status. | No participant management, scan, correction, configuration, admin or general alerts. |
| Participant | Own verified account registration/credential/attendance/certificate; self-cancel only before cutoff and first check-in. | No other records or staff actions. |
| Guest | Same own-record rights only under current OTP-verified ownership; guest self-cancellation requires OTP. | No permanent account assumption or staff permission. |

PUBLIC Published discovery is anonymous but field-allowlisted. PRIVATE Published detail uses an opaque, event-scoped, server-verifiable controlled link as both discovery route and bearer authority; possession of a valid link suffices for the same allowlisted details without account login or guest OTP. At most one link is active per PRIVATE event. Only the owning Organizer may issue, revoke or reissue it; replacement invalidates the previous proof immediately. There is **no automatic time-based PRIVATE-link expiry in MVP**: proof authorizes detail only while recognized as active, associated with the PRIVATE event, and the event remains Published. Explicit revocation/replacement, leaving Published, or leaving PRIVATE visibility ends access; a PRIVATE-to-PUBLIC edit invalidates the old proof atomically. Invalid, revoked, malformed, mismatched, non-PRIVATE/non-Published and unknown/unauthorized private reads receive the same `404 PRIVATE_UNAVAILABLE` response without confirming existence. A guessed ID is not access. The link never grants management or registration ownership; later registration still requires verified account or guest OTP. No recipient-bound invitation or dedicated rotation dashboard is in Slice 3. Public requests reveal no participant/internal/live data. Resource ownership checks apply to artifact download and delivery status as well as JSON metadata.

Middleware authenticates and attaches actor/correlation; controllers parse and validate; application services call a central action/resource policy before data reads or writes. Repositories scope queries by event/owner rather than fetch-all/filter-later. High-impact commands re-check assignment and lifecycle **inside** the transaction to prevent time-of-check/time-of-use gaps. Socket.IO handshake and room join check the same policy, and payload serializers use role-specific allowlists. Unauthorized actions return 401 when proof is absent, 403 when clearly forbidden, or privacy-safe 404 when revealing a private resource would leak existence. Denials do not mutate state; privileged denial attempts and grants/revocations are audited without secrets. Audit actor distinguishes account, guest proof context, and system job, with initiating actor retained for asynchronous work.

The approved Slice 2 session/cookie, CSRF, and guest-proof foundation remains in force. In Slice 3 the application shell may remember and select an Event + effective authorized Role for display/navigation, including multiple roles for one Event; a single currently authorized context is selected automatically, and a remembered choice is restored only if still authorized after login. That local context is a UI convenience, never an authorization token or new account/role grant. Every protected backend request still verifies session, Event scope, current role/assignment and requested permission independently; changing the selector grants nothing, and lost assignment removes the affected UI context. No global Admin or cross-event authority is introduced. MFA for staff, rate limits, and broader retention remain separately scoped. For Slice 3 the controlled URL uses `/private#access=<opaque-proof>` under a configured public origin; the browser holds proof in memory and sends `Authorization: PrivateLink <opaque-proof>` to `GET /api/v1/discovery/private`, with no account/guest proof merely to view. The fragment is stripped after capture; no API query/path, localStorage or sessionStorage bearer. The server stores only a protected non-reversible verifier, not raw proof; protected encrypted same-key issuance replay is bounded to 24 hours and is **not** link expiry. Responses are `no-store`, referrers and telemetry are redacted, and proof never appears in ordinary logs/audit. Link issue/revoke/reissue require owner account session, CSRF, event revision, idempotency, atomic audit and an at-most-one-active invariant. Server-side recognition/revocation, secure transport/storage, XSS/CSRF controls as applicable and negative wrong-event/old-proof tests remain mandatory. No TTL is configured for an active MVP link.
