# P0-E aggregate OTP abuse protection

Public account and guest challenge requests can otherwise generate repeated outbound messages after each challenge cooldown. The shared enforcement boundary is `OtpService.request`; HTTP-only throttling would miss internal callers. Normalization and channel availability checks precede admission. The existing sender, challenge-specific HMAC, constant-time verification, five-minute expiry, sixty-second cooldown, five attempts, latest-active semantics, contact locking, audits and account/guest separation are preserved.

EMAIL admission accepts a single bare mailbox and rejects SMTP display/list/comment/quote/backslash/control syntax before creating a challenge. Otherwise SMTP could deliver different hashed address strings to the same mailbox. The aggregate contact key also canonicalizes Unicode domains with IDNA, so equivalent Unicode/ASCII domain spellings cannot evade it. Existing identity hashes, stored contacts and verification normalization are unchanged; canonicalization applies only to the new abuse key.

## Admission and configuration

| Layer                                                       | Environment variables                               | Defaults                    |
| ----------------------------------------------------------- | --------------------------------------------------- | --------------------------- |
| Normalized contact, shared across account/guest purposes    | `OTP_CONTACT_LIMIT`, `OTP_CONTACT_WINDOW_SECONDS`   | 10 requests / 3600 seconds  |
| Canonical request source, across contacts/purposes          | `OTP_SOURCE_LIMIT`, `OTP_SOURCE_WINDOW_SECONDS`     | 120 requests / 600 seconds  |
| Application OTP admission, across channels/purposes/sources | `OTP_PROVIDER_LIMIT`, `OTP_PROVIDER_WINDOW_SECONDS` | 500 requests / 3600 seconds |

These are application defaults, not assumptions about Brevo's quota. Operators must align the application budget with their selected service capacity and traffic. Limits are positive decimal integers up to 1,000,000; windows are positive integer seconds up to 86,400. All replicas must share configuration and the existing stable OTP/contact keys. Changing a window or rotating keys creates a new budget identity; deploy such changes consistently and account for the fresh capacity.

The provider layer counts admitted requests, including cooldown requests and unknown PHONE account requests that do not produce delivery. This conservative policy prevents account existence from affecting provider saturation. A denial rolls back all reservations and challenge changes. Valid requests consume capacity only when their challenge transaction commits, including an admitted cooldown result. Rejected input, unavailable channels and failed transactions consume no capacity. The chosen contact allowance is well above an ordinary sign-in plus retries, while preventing a contact from sending once per minute indefinitely; the source allowance accommodates shared networks. Fixed windows may admit a burst on either side of a window boundary.

## Source trust

Express has no existing `trust proxy` policy. OTP source resolution is feature-local and does not change session, Origin/CORS or authorization behavior. `OTP_SOURCE_MODE` must be explicit in production:

- `direct`: use the socket peer, canonicalizing IPv4-mapped IPv6 and IPv6 spellings; ignore all client forwarding headers. Use only for direct client connections, not a shared production reverse proxy.
- `forwarded`: require `OTP_TRUSTED_PROXY_CIDRS`, accept X-Forwarded-For only from a matching socket peer and walk right to left to the first untrusted address. The configured proxies must append/overwrite accurate peer information. Chains are bounded to sixteen addresses.
- `railway`: legacy explicit-proxy mode; require `OTP_TRUSTED_PROXY_CIDRS`, accept one valid X-Real-IP only from a matching socket peer. Its validation is retained for separately verified topologies. The repository Caddy configuration does not establish a trusted source boundary for the public Vercel-to-Railway deployment. Do not guess Railway ranges or broaden trust to private networks.
- `signed_gateway`: required for the approved Vercel-to-Railway deployment. Require `OTP_SOURCE_SIGNING_KEY`: an independent random 32-byte key encoded as exactly 64 lowercase hex characters, distinct from JWT/contact/OTP/forecast keys. Reject any `OTP_TRUSTED_PROXY_CIDRS` setting, including an empty value. Accept only a verified source assertion; no socket, forwarding-header or internal-source fallback exists on either HTTP challenge route.

### Signed gateway contract and threat boundary

Browser challenge POSTs go to the same-origin Vercel Node function at `/api/v1/auth/account/challenge` or `/api/v1/auth/guest/challenge`, which calls the fixed configured HTTPS `RAILWAY_API_ORIGIN`. Other auth/API calls retain `VITE_API_ORIGIN`. The function uses Vercel's platform-owned `x-vercel-forwarded-for` metadata only, rejecting absent, duplicate/comma-merged or malformed values. See [Vercel request headers](https://vercel.com/docs/headers/request-headers) and [Node Web Standard handlers](https://vercel.com/docs/functions/runtimes/node-js). Deploy this function only on Vercel's protected ingress; running it behind an arbitrary HTTP server does not authenticate a client-supplied platform header. An additional proxy ahead of Vercel may group users under that proxy's platform-observed address; do not recover a source from client forwarding headers.

The internal `X-EOC-OTP-Source` header is `base64url(payload).base64url(HMAC-SHA256)`, with no padding. MAC input is the UTF-8 string `eoc-otp-source:v1:` followed by the encoded payload; the HMAC key is the decoded 32-byte signing key. Payload is compact UTF-8 JSON containing exactly these fields:

| Field         | Value                                                                 |
| ------------- | --------------------------------------------------------------------- |
| `version`     | Integer `1`                                                           |
| `audience`    | Literal `eoc-otp-source:production`                                   |
| `source_ip`   | Canonical asserted IP                                                 |
| `issued_at`   | Integer Unix time in seconds                                          |
| `method`      | Literal `POST`                                                        |
| `path`        | One of the two exact challenge paths, without query or trailing slash |
| `body_sha256` | Lowercase SHA-256 hex digest of the exact request body bytes          |

Gateway field order is the table order. The API accepts only compact `JSON.stringify`-equivalent JSON (no duplicate fields, escapes that change representation or extra whitespace), canonical unpadded base64url and the closed field set. Both ends validate IP literals with Node `isIP`, reject zones/ports/brackets/lists, serialize IPv6 using URL hostname normalization and convert IPv4-mapped IPv6 to dotted IPv4. The assertion must already contain the canonical representation. Interoperability tests cover IPv4, IPv6 and both mapped spellings.

The API rejects duplicate assertion headers, headers over 2048 bytes, wrong version/audience/method/exact path/body, invalid MAC, age over 60 seconds and future timestamps over 5 seconds. MAC comparison uses `timingSafeEqual` after an exact length check. Its existing strict 16 KiB JSON parser verification hook hashes raw bytes; it never reserializes parsed input. Compressed challenge bodies are rejected so decompression cannot change the binding. Other parsers/verification routes are unchanged. A source failure returns the existing generic `503 DEPENDENCY_UNAVAILABLE` before any OTP service call, challenge write, budget reservation or delivery callback. Malformed JSON and normal input validation retain their existing handling.

Threat reasoning: an untrusted browser can choose contact/body and spoof arbitrary headers; it cannot choose the signed source without the server key. The API's authorization to charge a source budget comes only from a valid short-lived assertion bound to that exact request. Direct public/private Railway requests and forged source headers fail closed. This authenticates the admission source, not an account or session. The gateway constructs only Content-Type, Origin, a generated correlation ID and the assertion; it forwards no cookie, authorization, client assertion or forwarding headers. It checks same-origin requests and retains the API's exact Origin policy. It follows no redirects, performs one fetch without retries, aborts upstream work after ten seconds, bounds request/response bodies to 16 KiB and returns `Cache-Control: no-store`. Only the existing safe pending/error envelope is returned; upstream headers and arbitrary fields cannot expose an assertion or credential.

Key ownership belongs to the protected Railway API and Vercel Node runtime. Never place it in `VITE_*`, frontend source/build arguments, logs or browser responses. Production Vercel variables must be scoped to Production only; previews/development require a separate API and separate keys. The audience is a protocol literal; key/environment separation prevents preview access to production. Signing-key rotation does not rotate OTP budget identities. Coordinate both deployments; mismatched keys temporarily fail closed. Clocks must stay within the five-second future tolerance. Assertions permit exact replay during the 60-second validity period; no nonce/state store is added. Every admitted replay still charges the unchanged transactional budgets and cooldown, and the assertion never reaches the browser.

Proxy modes fail closed on an untrusted peer, missing/invalid header or ambiguous metadata; they do not quietly group everyone under the proxy's IP. Direct mode is the development default. No trusted proxy range is guessed or installed automatically. Internal direct service callers without HTTP context share a durable `internal` source budget; they still reserve contact and application capacity. No raw source identity is persisted or returned to clients.

## Atomicity, storage and failures

The additive `OtpRateLimitBucket` table has a composite `(category,key,windowStart)` primary key, a positive count constraint, category/expiry constraints and an expiry index. Keys are domain-separated keyed HMACs, not raw contacts/IPs. Database `clock_timestamp()` determines epoch-aligned windows consistently across application instances. Parameterized PostgreSQL UPSERT increments only while below the limit, with row locking; all three reservations and challenge/audit writes share a transaction. A consistent PROVIDER, SOURCE, CONTACT order prevents competing budget-lock order cycles. Existing contact locks still protect challenge issuance/verification. Admission-store errors return generic temporary unavailability and cannot reach delivery. Other authenticated APIs never access the limiter.

There are no per-request permanent rows. Each bucket expires one day after its window ends (at most two days after its start). Each successful admission transaction deletes up to 200 indexed expired rows with SKIP LOCKED. Cleanup is lazy: idle buckets remain until traffic resumes, and denied/rolled-back transactions do not commit cleanup. Successful traffic removes old rows faster than it creates new ones (at most three per admission). The application admission cap also bounds new contact/source bucket creation; exhaustion cannot create rows indefinitely. No worker or external infrastructure is added.

Committed reservations are never refunded, including definite/ambiguous provider failures, process failure or abandoned delivery callbacks. They expire with their window, so failure costs are finite and attackers cannot exploit reserve/refund loops. A delivery callback attempts sending at most once. Failed delivery keeps existing challenge consumption/audit handling. Brevo retains HTTPS, its ten-second timeout, bounded acceptance parsing, no response-body logging and no SMTP fallback.

Aggregate denials use one generic 429 without category/count/quota details or existence-dependent retry timing. Operator Pino warnings contain only CONTACT/SOURCE/PROVIDER and `delivery_attempted:false`; normal admissions add no limiter log or PII-heavy audit trail. Existing issuance/delivery/failure audits distinguish whether sending proceeded. OTP values, contact hashes, raw sources, tokens and credentials never enter limiter logs.

## Validation and deployment

Focused PostgreSQL tests exercise each budget, concurrency across independent clients/services, normalized-contact purpose sharing, request/source spoofing, window rollover, bounded cleanup, fail-closed admission, enumeration, failed-delivery reservations and one-use callbacks. Signed-source tests additionally verify request binding, both purposes, source-budget isolation, global contact/provider budgets, concurrent reservations, lifecycle and privacy. Config/assertion/gateway tests cover invalid keys/MACs/metadata, trust bypass, routing, redirect rejection, timeout and no retries. Existing auth/Brevo/session/staff/registration suites retain legitimate signup/login, guest proof, registration and permission coverage. The existing additive-upgrade tests retain their schema checks. This source fix adds no schema or migration; the existing OTP budget migration must already be applied. Repository tests do not certify live Vercel routing/metadata or Brevo delivery. Deployment acceptance must verify both browser challenge paths, spoofed platform/forwarding headers, unsigned Railway denial without challenge/budget writes, distinct external-source budgets, SPA deep links and real provider delivery, using non-secret evidence only.
