## 1. Publication gate: exact source comparison

| Source | Current statement | Consequence |
| --- | --- | --- |
| [UC-02](../requirements/USE_CASES.md), Preconditions | A Draft has required capacity, schedule/time zone, registration policy **and gate configuration for publication**. | Publication readiness appears to reject a gate-less Draft. |
| [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), Transition baseline | Draft → Published requires valid required configuration under `FR-EVT-002` and `FR-EVT-004`; Published → Live explicitly requires **at least one configured gate**. | A gate is explicitly rechecked at Live. The Draft → Published row does not explicitly say whether a gate is among its required fields. |
| `FR-EVT-002`, `FR-EVT-004` in [REQUIREMENTS.md](../requirements/REQUIREMENTS.md) | Publication blocks until required configuration is valid and explains gaps; one gate is required **before live operation**. | These requirements do not explicitly prohibit an earlier publication gate requirement, nor do they independently require one at publication. |
| [UC-01](../requirements/USE_CASES.md), `US-ORG-01`, `US-ORG-02` in [USER_STORIES.md](../requirements/USER_STORIES.md), [PRD](../PRD.md), “Organizer lifecycle” | A partial Draft may be saved; Organizer sees publication blockers. The PRD journey lists gate configuration before publication. | Partial Draft remains valid; the PRD and `UC-02` support a stricter publication guard. |
| [ROLE_PERMISSION_MATRIX.md](../requirements/ROLE_PERMISSION_MATRIX.md), `OPD-01`, `OPD-17` in [OPEN_PRODUCT_DECISIONS.md](../requirements/OPEN_PRODUCT_DECISIONS.md) | Organizer alone publishes/starts/completes/cancels; Organizer and assigned Admin may create/update gates. | Guard timing does not change who may transition or configure a gate. |

**Finding:** This is **not a formal logical contradiction**. Requiring a gate at publication *and* rechecking it on Published → Live satisfies every quoted statement; the Live guard is not worded as the **first** time a gate is needed. It is nevertheless a material **readiness ambiguity**: the lifecycle table does not explicitly identify the publication gate blocker, while `UC-02` does. A screen and test cannot safely choose a publication readiness list from the table alone.

## 2. Recommended resolution for human approval

**Recommendation R1 (not yet approved):** require at least one **configured** gate before Draft → Published, and independently recheck that condition before Published → Live. Keep saving partial Drafts. This makes `UC-02` and the PRD journey literal, preserves the explicit Live safety guard, and does not change Organizer-only transition authority or registration availability. It is the smallest textual clarification: add the gate to the lifecycle publication guard and explain that the Live check is a fresh check, not a newly introduced requirement. `FR-EVT-004` (“before live operation”) remains satisfied; a short clarification to `FR-EVT-002` and `FR-EVT-004` is advisable so the publication blocker is traceable rather than inferred.

**Alternative requiring approval:** allow publication without a configured gate, then require one only to enter Live. That follows the minimum expressed by `FR-EVT-004` and the explicit Live guard, but requires changing the `UC-02` publication precondition and the PRD organizer journey. It permits a Published event and potentially open registration before a gate exists. Neither interpretation may be implemented until the product owner chooses.

**Approval question D1:** Is a configured gate mandatory at **both publication and Live** (R1), or **only at Live**? If R1, define what “configured” minimally means under D5 below. Do not equate a Gate row created for Slice 2 authorization tests with an operationally configured gate.

**Documents to amend only after D1 approval:** `UC-02` in [USE_CASES.md](../requirements/USE_CASES.md) if the Live-only alternative wins; otherwise [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md) Draft → Published guard and a short `FR-EVT-002`/`FR-EVT-004` clarification in [REQUIREMENTS.md](../requirements/REQUIREMENTS.md). Review [PRD.md](../PRD.md) organizer journey, [SCREEN_INVENTORY.md](../design/SCREEN_INVENTORY.md) `S-ORG-02`/`S-ORG-03`, [UX_STATES.md](../design/UX_STATES.md), [TRACEABILITY.md](../requirements/TRACEABILITY.md), [SLICE_3_UI_PLAN.md](SLICE_3_UI_PLAN.md), and Slice 3 acceptance tests/readiness copy for consistency. No underlying document is changed in this pass.

## 3. Four contract gaps: source, missing decision, minimum proposal

The following are **proposed minimum contract shapes, not final paths, payload schemas, or implementation choices**. Each must be reviewed against the [API contract’s common command/error rules](../api/API_CONTRACT.md) and [technical architecture](../architecture/TECHNICAL_ARCHITECTURE.md). The committed Slice 2 API has account proof/current actor, event assignments and assigned-gate scope, but no event list/detail/create/transition, public discovery, PRIVATE entry, or gate-configuration route (`backend/src/app.ts`, `backend/src/modules/auth/http.ts`, `backend/src/modules/staff/http.ts`). Its Prisma `Event`/`Gate` records contain only owner/Draft and gate identity/scope foundations (`database/prisma/schema.prisma`).

### D2 — Staff event list and detail

- **A. UI requires:** `S-ORG-01` needs an owned/assigned event list with identity, state and enough schedule/context to select an event; `S-ORG-02` needs authorized event detail, saved configuration, revision, readiness blockers and permitted controls. Empty, forbidden, stale-version and unknown-result states must be distinguishable.
- **B. Already provided:** `GET /api/v1/auth/me` exposes Organizer capability and assignment event IDs, not event detail; existing assignment reads are event-scoped. [Phase 2 auth/RBAC](../security/AUTH_RBAC_ARCHITECTURE.md) requires server-resolved actor/action/event/resource scope, deny-by-default and privacy-safe errors. [API_CONTRACT.md](../api/API_CONTRACT.md) sets opaque IDs, cursor-paged lists, UTC times/IANA zone, correlation IDs, current revision and safe errors.
- **C. Planned, not implemented:** The API contract’s “Events” row names create, PATCH details/policy and transition operations with registration-availability reasons/revision. [API_PLAN.md](../api/API_PLAN.md) names `/events` as a representative resource; neither file supplies final staff list/detail reads or schemas. [Database architecture](../architecture/DATABASE_ARCHITECTURE.md) defines owner/event/gate/assignment relationships conceptually.
- **D. Genuinely missing:** Explicit scoped list and detail/readiness **read contracts**; exact allowed field sets for Organizer versus assigned Admin; final create/edit/transition request and response schemas; field-level publication/Live guards and version/unknown-result recovery. **NEW contract decision required.** A browser-supplied event ID or Organizer-capability flag cannot by itself authorize another event.
- **E. Minimum proposed contract:** authenticated owned/assigned event list with stable opaque event ID, display identity, lifecycle state, schedule/time zone and cursor semantics; authenticated event detail with configured values, server-derived readiness blockers, revision/as-of and role-appropriate editable/action permissions; create/edit/transition commands use server ownership/assignment checks, current-version protection, atomic required audit and the common error envelope. Exact URLs, field allowlist, filtering/order and role-specific edit allowlist require approval. Do not return other organizers’ Drafts or internal/private data through public reads.

**Approval question D2:** Approve the minimum staff list/detail/readiness resource boundary and **which configuration fields an assigned Event Admin may edit** in Draft/Published, while keeping lifecycle, registration times/manual closure, ownership transfer and Admin grants Organizer-only. Approve final route/field/error/revision details in the Slice 3 API specification before UI implementation; this review does not choose them.

### D3 — PRIVATE controlled-link entry

- **A. UI requires:** `S-PUB-01` must omit PRIVATE events; `S-PUB-02` must show allowlisted Published details after legitimate controlled entry, or a non-leaking unavailable result. The visitor must not need a permanent guest account merely to reach an allowed detail page.
- **B. Already provided:** `OPD-02`, `FR-DISC-001` and the [role matrix](../requirements/ROLE_PERMISSION_MATRIX.md) lock PUBLIC/PRIVATE visibility and public-field allowlist. [AUTH_RBAC_ARCHITECTURE.md](../security/AUTH_RBAC_ARCHITECTURE.md) says a guessed ID is not PRIVATE access. Slice 2 guest OTP proof exists for guest ownership, **not** as an established PRIVATE invitation credential.
- **C. Planned, not implemented:** The API contract’s “Discovery” row provides conceptual anonymous PUBLIC catalog/details and controlled PRIVATE Published detail reads, with safe `NOT_FOUND`/unavailable behavior. [TECHNICAL_ARCHITECTURE.md](../architecture/TECHNICAL_ARCHITECTURE.md) explicitly defers the PRIVATE-link mechanism.
- **D. Genuinely missing:** What authorizes the controlled entry: possession of an opaque link capability, a recipient-bound invitation with verification, or another explicitly approved mechanism; how access is conveyed/validated and revoked/expired; non-leaking error semantics and sharing policy. **NEW security/product contract decision required.** Do not silently treat `eventId`, guest OTP or a generic public URL as authorization.
- **E. Minimum proposed contract:** a PUBLIC catalog query that can never return PRIVATE rows; a Published detail read that checks visibility and, for PRIVATE, a server-validated controlled-entry proof before returning only allowlisted fields; uniform privacy-safe rejection for absent/forbidden private resources; no protected participant/operational data in either response. Final proof format, issuance/distribution, expiry/revocation, replay/sharing and URL/transport form require human/security approval.

**Approval question D3:** Choose the controlled-entry authority and its minimum sharing/revocation/expiry policy. The existing documents permit a controlled link **or** invitation but do not select the mechanism.

### D4 — Registration-availability response

- **A. UI requires:** `S-PUB-02` and `S-ORG-02` must distinguish event state from registration availability and explain publication-default/future opening, configured/default event-start close, manual Organizer closure, capacity-only closure, Live closure and Cancelled state. They must not promise a registration action in Slice 3.
- **B. Already provided:** [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), `OPD-13` and `OPD-18` lock these distinct causes, one capacity as a `REGISTERED` **registration cap**, and no separate gate cap. `OPD-02` permits public availability and remaining/available indication but not live occupancy or internal data. [DATABASE_ARCHITECTURE.md](../architecture/DATABASE_ARCHITECTURE.md) says availability is derived from lifecycle, times, `REGISTERED` count and manual flag.
- **C. Planned, not implemented:** The API contract’s “Events” and “Discovery” rows promise event state plus registration availability/reasons; the “Registration” row gives future enforcement errors. Slice 4 owns the `Registration` table and atomic cap/duplicate checks. There is no current registration count or registration API.
- **D. Genuinely missing:** Exact public/staff availability response fields, stable reason catalog, multiple-cause presentation/precedence, authoritative `as_of` time and treatment of remaining/available indication **before** Slice 4 facts exist. **NEW contract decision required.** A fabricated `REGISTERED` count, cap-full demonstration or available registration CTA in Slice 3 would be misleading.
- **E. Minimum proposed contract:** one server-derived availability result separate from lifecycle state, with an open/closed indication, applicable blocker reason(s), relevant opening/closing time when authorized, and calculation time. For the Slice 3-only state, report only reasons knowable from event configuration and lifecycle; do not fabricate capacity usage or claim the registration endpoint exists. Decide whether public output uses a primary reason or all active causes, and how it indicates that remaining-slot data is unavailable until Slice 4. The UI must not imply registration can be submitted before that slice.

**Approval question D4:** Approve the reason/precedence and public-versus-staff data contract, especially how to display availability/remaining indication while no registration records or registration action exist. Keep capacity-only automatic reopening as a Slice 4 enforcement/test responsibility, not a fake Slice 3 state transition.

### D5 — Minimum gate setup

- **A. UI requires:** `S-ORG-03` needs a way for Organizer/assigned Admin to view/configure an event’s gate(s) and show whether the approved lifecycle guard is met. Staff assignments can reference a valid gate, but this is not the scanner UI.
- **B. Already provided:** Slice 2 persists `Gate(id,eventId)` for scope and exposes assigned-gate scope and staff-assignment routes. The [role matrix](../requirements/ROLE_PERMISSION_MATRIX.md) allows Organizer and assigned Admin to create/read/update gates, denies ordinary delete, and limits Gate/Security to its assigned gate. `FR-EVT-004` requires at least one gate before Live.
- **C. Planned, not implemented:** [API_PLAN.md](../api/API_PLAN.md) names representative `/events/{eventId}/gates` configuration/operational resource; [DATABASE_ARCHITECTURE.md](../architecture/DATABASE_ARCHITECTURE.md) assigns Gate to Event. [SLICE_2_PLAN.md](SLICE_2_PLAN.md) assigns real gate configuration needed for Live to Slice 3 and scanner operations to Slice 5.
- **D. Genuinely missing:** A working gate list/create/update/read contract, minimum fields and validation defining **configured**, impact of gate edits/removal on Published/Live readiness and existing assignments, and whether any staff assignment is a guard (no source currently requires one). **NEW contract/guard decision required.** The fixture-grade Slice 2 Gate row cannot be assumed operationally configured.
- **E. Minimum proposed contract:** event-scoped gate list/read plus authorized create/update of only the minimum fields selected under the “configured” definition; response gives stable gate identity/event association and server-derived readiness. Recheck the approved gate guard inside lifecycle transition authorization. Preserve assigned-event Admin gate authority, Organizer-only transitions and existing grant scope. Do not add scanning, device health, attendance, occupancy, gate-capacity limit, unrestricted delete or staff-assignment prerequisite without separate approval.

**Approval question D5:** What minimum gate configuration makes the gate count as configured, and what happens to readiness when that configuration is changed? Confirm that a staff assignment is **not** an additional publication/Live guard unless the product owner expressly adds it.

## 4. Slice 3 boundary after reconciliation

The [roadmap’s Slice 3 row](../ROADMAP_PHASE_2.md) still owns real Organizer Draft/configure/publish/Live/complete/cancel, PUBLIC allowlisted discovery, PRIVATE controlled entry, registration-availability explanation and the narrow gate setup needed for the lifecycle guard. Reuse committed Slice 2 identity/Session/CSRF, owner/assignment authorization and audit foundations. Event Admin can edit only within approved assigned-event scope and cannot perform lifecycle transitions, transfer ownership or grant another Admin. A Cancelled event is terminal for new registration/check-in; any existing registration rows must remain unchanged once they exist in later slices.

**Outside Slice 3 implementation:** registration and QR credential lifecycle (Slice 4); gate scanner, `scan_id`, attendance and occupancy (Slice 5); authoritative live command center/Socket.IO snapshot (Slice 6); alerts (Slice 7); advisory occupancy forecasting (Slice 8); bounded volunteer **task** flow (Slice 11); certificate eligibility/issue/delivery (Slices 9–10). Their future guards may rely on Slice 3 event state, but this review neither creates their routes/tables nor claims their UI works. No generic feed, full calendar, Kafka or second physical-capacity rule is introduced.
