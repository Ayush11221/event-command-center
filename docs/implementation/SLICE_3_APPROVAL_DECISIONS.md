## 1. Decision 1 — Gate requirement

**Current repository evidence.** [UC-02](../requirements/USE_CASES.md), Preconditions, explicitly includes gate configuration **for publication**. [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), Transition baseline, explicitly checks at least one configured gate for **Published → Live**; its Draft → Published row refers to valid required configuration without enumerating a gate. `FR-EVT-002` requires explained publication validation, and `FR-EVT-004` requires a gate before live operation. The [PRD organizer journey](../PRD.md) places gate setup before publishing. [OPD-01](../requirements/OPEN_PRODUCT_DECISIONS.md) and the [matrix](../requirements/ROLE_PERMISSION_MATRIX.md) make transitions Organizer-only; Organizer/assigned Event Admin may configure gates. These statements can coexist: a Live guard does not imply no publication guard.

**Proposed decision (not approved).** A Draft may be saved incomplete, but Draft → Published requires at least one configured gate; Published → Live rechecks that at least one configured gate still exists. Organizer alone invokes both transitions. A missing gate appears as a publication/Live readiness blocker, not as a new lifecycle state. “Configured” needs Decision 5.

**Exact lifecycle implication and why Slice 3 needs it.** Under this proposal, a gate-less Draft cannot publish or appear in PUBLIC discovery; a Published event whose required gate is no longer present cannot become Live. Registration availability remains a separate policy and does not itself create or remove a gate. Slice 3 readiness UI and transition tests need the same guard as the server.

**Alternative still open.** Require a configured gate only for Published → Live, permitting publication without one. This satisfies the literal minimum in `FR-EVT-004` but changes the `UC-02` precondition and PRD sequence. Do not implement either interpretation on the strength of this document.

**Exact documents/contracts affected after approval.** If the proposal wins, clarify Draft → Published in [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md) and `FR-EVT-002`/`FR-EVT-004` in [REQUIREMENTS.md](../requirements/REQUIREMENTS.md); synchronize [UC-02](../requirements/USE_CASES.md), [SCREEN_INVENTORY.md](../design/SCREEN_INVENTORY.md), [UX_STATES.md](../design/UX_STATES.md), [TRACEABILITY.md](../requirements/TRACEABILITY.md), [SLICE_3_UI_PLAN.md](SLICE_3_UI_PLAN.md), and the eventual lifecycle/readiness API contract/tests. If Live-only wins, change the `UC-02` precondition and [PRD](../PRD.md) journey first, then align those downstream files. No authoritative file is changed now.

**REQUIRES HUMAN APPROVAL:** gate before both Publish and Live, or Live only.

## 2. Decision 2 — Event list/detail/edit contract

**Current repository evidence.** `FR-EVT-001` grants Organizer owned-Draft creation and assigned Admin Draft editing; `FR-EVT-003`, `OPD-01` and `OPD-17` in the [decision register](../requirements/OPEN_PRODUCT_DECISIONS.md) reserve lifecycle/ownership to Organizer. `FR-EVT-005` permits Organizer Published-detail edits with visible/audited material changes and restricts Live registration/attendance policy changes. The [role matrix](../requirements/ROLE_PERMISSION_MATRIX.md) grants Organizer and assigned Admin event/configuration reads, assigned Admin gate create/read/update and permitted event configuration/capacity updates, but says the Admin edit scope is **approved** without enumerating every field. It denies Admin lifecycle, registration-time and manual-closure controls, ownership transfer and Admin grants. [API_CONTRACT.md](../api/API_CONTRACT.md), “Events,” plans create, details/policy edit, transition, revision, readiness and availability reasons but does not finalize list/detail methods or field schemas. Current Slice 2 `GET /api/v1/auth/me` returns capability/assignment IDs, not an event list or detail; the current `Event` record has owner, Draft state and ID only.

**Proposed minimum decision.** Approve *two server-scoped reads* (owned/assigned list and management detail) plus final create/edit/transition contracts. Do not infer editable fields from a read response. The minimum six-role/action mapping is:

| Actor/task | Minimum data or permission supported | Boundary still to approve |
| --- | --- | --- |
| Organizer event list (`S-ORG-01`) | Only events owned by the authenticated Organizer; event identity, lifecycle state and schedule/time-zone context sufficient to select one. | Final list field set, ordering/filtering and cursor limits. Organizer capability does not reveal other owners’ events. |
| Event Admin assigned-event list (`S-ORG-01`) | Only events with a current assigned Event Admin grant; same selection context plus clear assigned scope. | Final list field set; role combination/multi-event presentation must not broaden server scope. |
| Organizer event detail (`S-ORG-02`) | Own event configuration, lifecycle/readiness, registration-availability causes, gates and permitted management actions. | Exact response field set and whether sensitive/internal evidence needs a separate read. |
| Event Admin event detail (`S-ORG-02`) | Assigned event configuration/capacity and gate context needed for permitted operations, with lifecycle/availability shown as read-only. | Exact field minimization and editable-field indicators; read access is not transition authority. |
| Organizer edit event | Configure owned Draft; edit Published **details** with material-change visibility/audit; configure opening/closing times and manual close/reopen; control lifecycle through transition actions, not generic edit. | Exact Published editable-field allowlist and any Live non-policy edits require approval. |
| Event Admin edit event | Edit assigned Draft within `FR-EVT-001`; create/read/update assigned-event gates; edit only specifically approved operational settings/configuration/capacity within the matrix. | The individual non-gate event fields and Published edit extent are **not enumerated**; no generic “edit all” permission may be inferred. |

**Field distinction for the approval.** Existing documents name event/public details (name, description, date/start/end, public venue/location, organizer-provided image/banner, public category/tags), PUBLIC/PRIVATE visibility, schedule/IANA zone, one `REGISTERED` registration capacity, optional opening/closing times, manual closure, registration cancellation cutoff, optional check-out, gates and lifecycle state (`OPD-02`, `OPD-04`, `OPD-06`, `OPD-13`, `OPD-18` in the [decision register](../requirements/OPEN_PRODUCT_DECISIONS.md), [DATABASE_ARCHITECTURE.md](../architecture/DATABASE_ARCHITECTURE.md)). For Organizer, Draft configuration of these *as applicable* follows ownership; Published detail edits are explicitly allowed, while the exact policy-field edit set is not fully specified. Registration opening/closing times and manual close/reopen are expressly Organizer-only. Lifecycle state is changed only by Organizer transition commands; ownership and Event Admin grants are not ordinary event-edit fields. For Event Admin, gate configuration is explicitly permitted; the matrix permits assigned-event configuration/capacity updates **within approved scope**, but does not settle which of name/description, schedule, visibility, capacity, cutoff or check-out settings may be changed. Do not grant any of those individual edits until their allowlist is approved. Once Live, registration/attendance policy changes are restricted for both roles; which harmless detail edits remain possible is also unresolved. Completed/Cancelled have no MVP reopening, while post-terminal edit permission is not defined and must not be inferred.

**Public versus management detail.** [FR-DISC-001](../requirements/REQUIREMENTS.md) and `OPD-02` allow a public Published detail to expose **only** name, description, date/start/end, public venue/location, organizer-provided image/banner, registration availability, remaining/available registration indication and public category/tags. It excludes participant/contact, QR, internal operations, live occupancy, alerts, admin data and audit. Authenticated management detail may include owner/assignment context, configuration, gate/readiness and revision under event scope; it must not be reused as a public serializer. PRIVATE detail additionally needs Decision 3 authority.

**Minimum proposed Slice 3 API contract, not final signatures.** (1) authenticated, server-filtered owned/assigned event list with opaque IDs, selection fields and cursor semantics; (2) authorized management detail with server-derived current state, configuration, readiness blockers, registration-availability causes, permitted actions and revision/as-of; (3) Organizer create Draft, scope-checked edit and Organizer-only transition operations as already planned; (4) version/validation/unknown-result behavior, correlation ID and required audit per the Phase 2 contract. The server derives actor and scope on every read/write; browser role/owner/event IDs are never authorization proof. Final URLs, payloads, Admin field allowlist, Published/Live edit rules and public-versus-management serializers remain contract decisions.

**Why needed for Slice 3.** `S-ORG-01` and `S-ORG-02` cannot select, edit or explain readiness from `/auth/me` assignment IDs, and a generic event PATCH would risk Admin escalation or silent Live policy mutation.

**Exact documents/contracts affected after approval.** Record the field/action matrix in a Slice 3 API/OpenAPI contract and align [API_CONTRACT.md](../api/API_CONTRACT.md) if its representative boundary changes, [ROLE_PERMISSION_MATRIX.md](../requirements/ROLE_PERMISSION_MATRIX.md) only if approval changes permissions rather than clarifying “approved edit scope,” [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), [SLICE_3_UI_PLAN.md](SLICE_3_UI_PLAN.md), and matching screen/state and negative-authorization tests.

**Alternative still open.** A narrower Admin edit allowlist (gate setup only plus assigned Draft fields) versus additional specifically named operational settings/capacity edits. No alternative grants lifecycle, registration-time/manual closure, ownership transfer or Admin-grant authority.

**REQUIRES HUMAN APPROVAL:** exact Admin field allowlist and stage restrictions; minimum list/detail/readiness and create/edit/transition response contracts.

## 3. Decision 3 — PRIVATE controlled entry

**Current repository evidence.** `OPD-02`, `FR-DISC-001`, [UC-15](../requirements/USE_CASES.md) and the [role matrix](../requirements/ROLE_PERMISSION_MATRIX.md) say PRIVATE Published events are omitted from PUBLIC discovery and accessed via a controlled link/invitation without private-detail leakage. [AUTH_RBAC_ARCHITECTURE.md](../security/AUTH_RBAC_ARCHITECTURE.md) adds that guessing an event ID is not authorization; the [API contract](../api/API_CONTRACT.md) plans a PRIVATE Published detail read with privacy-safe unavailable/not-found response. The [technical architecture](../architecture/TECHNICAL_ARCHITECTURE.md) defers the PRIVATE-link mechanism. Slice 2 guest OTP proof is for guest ownership/registration, not an approved PRIVATE-detail grant.

**What is *not* established:** who issues or distributes entry, who may receive/use it, whether possession of the link alone suffices, whether account sign-in or guest/contact verification is required **to view details**, whether the link is an access credential versus a discovery pointer that leads to another proof step, and whether/how it expires or rotates/revokes. Registration itself later requires verified account or guest OTP (`OPD-03`); that does **not** answer PRIVATE detail access. Do not treat a guessed ID, ordinary URL or existing guest proof as sufficient by assumption.

**Proposed minimum decision/contract (not an implicit choice of mechanism).** Define a server-checkable controlled-entry authority for PRIVATE **Published** detail reads, separate from event ID; specify who may issue/distribute it, who may use it, whether it alone grants allowlisted detail or requires verified recipient proof, and its sharing/expiry/revocation rule. The PUBLIC catalog must never list PRIVATE events; the PRIVATE read returns only the `OPD-02` allowlist after authorization and otherwise gives a non-leaking unavailable result. Do not require a permanent guest account solely by inference. Exact token/link/transport design is an implementation contract **after** the authority choice.

**Why needed for Slice 3.** The roadmap assigns PRIVATE controlled entry to Slice 3. Without its authority boundary, even a visually correct page can leak an unlisted event or wrongly force/skip verification.

**Exact documents/contracts affected after approval.** Specify authority and safe responses in the Slice 3 API/security contract; update [API_CONTRACT.md](../api/API_CONTRACT.md), [AUTH_RBAC_ARCHITECTURE.md](../security/AUTH_RBAC_ARCHITECTURE.md) if their deferred mechanism is settled, [SLICE_3_UI_PLAN.md](SLICE_3_UI_PLAN.md), and discovery UX/test cases. Amend Phase 1 `OPD-02`/`FR-DISC-001` only if the approved choice changes their locked visibility/access rule.

**Alternatives still open.** A controlled link whose possession is sufficient for allowlisted detail, or an invitation that requires matching verified recipient proof; the repository selects neither. Link rotation/revocation and contact verification for **detail viewing** are not currently defined.

**REQUIRES HUMAN APPROVAL:** the controlled-entry authority, audience/verification condition and minimum expiry/revocation/sharing policy.

## 4. Decision 4 — Registration availability

**Current repository evidence.** [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), `OPD-13` and `FR-REG-001` separate event state from registration availability. `OPD-18` says one event capacity limits the number of `REGISTERED` registrations; this is not a physical gate capacity or live `INSIDE` count. [API_CONTRACT.md](../api/API_CONTRACT.md) plans availability/reasons in event and discovery responses, but gives no final fields/reason codes. Slice 4 owns actual registration, cap-count enforcement and capacity-only reopening ([roadmap](../ROADMAP_PHASE_2.md)); Slice 3 has no registration records or route.

**Supported distinctions, not new lifecycle states:**

| Event lifecycle | Registration availability or blocker already defined |
| --- | --- |
| Draft | Not discoverable/registrable. |
| Published before a configured future opening | Not yet open; absent opening time means open on publication, subject to other blockers. |
| Published within the allowed time/window | Open only if no manual closure and fewer than capacity `REGISTERED` registrations. |
| Published after configured close or default event-start close | Scheduled/event-based closed. |
| Published at `REGISTERED` cap | Capacity reached; new registration blocked. A pre-check-in cancellation reopens **only** if this was the sole blocker. |
| Published under Organizer manual closure | Manually closed; capacity release does not reopen it. Organizer alone may reopen. |
| Live | Registration closed regardless of later configured close time. |
| Completed or Cancelled | No new registration; Cancelled retains existing registrations unchanged and blocks check-in too. |

Multiple closure causes may coexist. “Not yet open,” “capacity reached” and “manually closed” are availability reasons, **not** event lifecycle states. A published event can be closed to registration; a cap-full registration list is not a live-occupancy alert. PUBLIC catalog inclusion is independently tied to Published visibility. [SCREEN_INVENTORY.md](../design/SCREEN_INVENTORY.md) and [UX_STATES.md](../design/UX_STATES.md) mention Live/Cancelled closure presentation, but the locked public-discovery allowlist explicitly describes **Published** catalog/details; what a visitor with a previously known public URL may see after leaving Published is not fully specified.

**Proposed minimum Slice 3 decision/response.** Keep `event_state` distinct from a server-derived registration-availability result. The latter needs whether policy permits registration, the applicable existing blocker reason(s), relevant configured opening/closing time or event-start default, and the server calculation time; public output remains within `OPD-02`’s allowlist, while management detail may explain more. This is a **conceptual field set**, not a final JSON schema or new state catalog. No public `REGISTERED` count, numerical remaining-slot claim or capacity-reached demonstration may be fabricated before Slice 4 exists. The Slice 3 UI must not present a functioning registration action or claim that the later endpoint can accept submissions. Approve whether public response shows one primary cause or all applicable causes and how “remaining/available” is represented when capacity facts are not yet available.

**Why needed for Slice 3.** The roadmap explicitly assigns availability reasons and PUBLIC details, but exposing an “open” registration CTA with no registration capability, conflating Live with registration capacity, or fabricating a cap count would mislead users.

**Exact documents/contracts affected after approval.** Finalize event/discovery availability fields and safe error meanings in the Slice 3 API contract; align [API_CONTRACT.md](../api/API_CONTRACT.md), [SLICE_3_UI_PLAN.md](SLICE_3_UI_PLAN.md), [SCREEN_INVENTORY.md](../design/SCREEN_INVENTORY.md) and [UX_STATES.md](../design/UX_STATES.md) if presentation changes. Preserve locked [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), `OPD-13` and `OPD-18` unless the human explicitly changes product policy.

**Alternatives still open.** One primary blocker versus all active blockers; safe unavailable response versus allowlisted closed-detail view for a formerly Published Live/Cancelled event reached by a known URL; and the precise pre-Slice-4 public “remaining/available” indication. No option may make Live/Cancelled catalog-visible without a new product decision.

**REQUIRES HUMAN APPROVAL:** availability response/reason presentation, public behavior before registration exists, and public treatment of known links after an event leaves Published.

## 5. Decision 5 — Configured gate definition

**Current repository evidence.** `FR-GATE-001` requires authorized gate configuration, and `FR-EVT-004` requires at least one gate before Live. [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md) calls it “at least one gate is configured.” The [role matrix](../requirements/ROLE_PERMISSION_MATRIX.md) grants Organizer and assigned Admin gate create/read/update but not ordinary delete; Gate/Security is limited to an assigned event/gate. [DATABASE_ARCHITECTURE.md](../architecture/DATABASE_ARCHITECTURE.md) defines a Gate belonging to an Event, with operator assignment/operational status as separate concepts. [SLICE_2_PLAN.md](SLICE_2_PLAN.md) says its minimal Gate is for authorization fixtures; real gate configuration belongs to Slice 3, scanning to Slice 5. Current Prisma Gate has only an ID and Event association; no name, device, location, readiness, staff or connectivity field is defined.

**Proposed minimum decision (not approved).** For the Slice 3 lifecycle guard, count a Gate as configured once an authorized Organizer or assigned Event Admin has created a persistent Gate associated with that Event through the approved gate-configuration workflow. At least one such current Gate must exist at the approved transition(s). The server, not a UI flag, checks the association. This uses only the existing Gate identity/event concept and does not make assigned staff, camera/scanner hardware, connectivity, operational health or a second capacity a prerequisite. A synthetic Slice 2 test fixture is not a product gate-setup workflow.

**Why needed for Slice 3.** A publication/Live readiness result cannot test an undefined “configured” predicate. The minimum above allows the guard without pulling scanner/session operation into Slice 3. If the UI needs a human-readable gate label, its exact field/validation is a **new presentation/data contract** to approve; it is not implied by the current Gate schema.

**Exact documents/contracts affected after approval.** Define the guard predicate and authorized gate list/create/read/update result in the Slice 3 API/data specification; align [EVENT_LIFECYCLE.md](../requirements/EVENT_LIFECYCLE.md), `FR-EVT-004` in [REQUIREMENTS.md](../requirements/REQUIREMENTS.md), [API_PLAN.md](../api/API_PLAN.md) if its representative gate boundary changes, [SLICE_3_UI_PLAN.md](SLICE_3_UI_PLAN.md) and lifecycle/gate permission tests. A schema/migration decision would follow later; none is made here.

**Alternative still open.** Require additional named gate configuration fields before counting it. The repository does not specify such fields, and device/connection/staff prerequisites are **not** approved by implication. Ordinary gate deletion is denied in the matrix, so any later deactivation/removal semantics need separate approval rather than an invented delete flow.

**REQUIRES HUMAN APPROVAL:** whether valid persistent Event–Gate association via authorized setup is sufficient, or which additional *named* field is required; this is coupled to Decision 1’s transition timing.
