## 1. Remaining PRIVATE-link decisions

The approved `OPD-02`/`FR-DISC-001` rule is a server-verifiable, event-scoped controlled link that is both discovery route and bearer authority for **allowlisted detail of its associated PRIVATE event while Published**. Possession alone suffices for that detail; neither account login nor guest OTP is required to view it. It grants no management, registration ownership, or later registration action. A guessed event ID is not proof. Invalid, invalidated, mismatched, non-Published, and unknown/unauthorized PRIVATE reads share one safe unavailable outcome. Organizer controls issuance/distribution. These are locked facts, not options below.

| Mechanic | Existing rule | Missing decision | Proposed MVP option — for approval only | Alternative |
| --- | --- | --- | --- | --- |
| Event scope and detail authority | Proof must resolve to its associated PRIVATE Published event and only public-allowlisted detail. | None. | Preserve exactly. | None within approved scope. |
| Independent expiry | Security architecture says the eventual mechanism must support expiry; no duration or start/renewal rule is set. Leaving Published already ends access but is not an independent TTL. | Exact lifetime and expiry trigger; behavior on expiry. | Set a bounded lifetime in the security contract, with a human-approved duration and start event; expired proof fails with the same safe unavailable response. No duration is selected here. | A different bounded expiry policy. An indefinite credential would need explicit security-architecture reconsideration. |
| Invalidation/revocation | Server checks that proof has **not** been invalidated; invalidation immediately ends detail authority. Organizer controls **issuance/distribution**, not expressly a standalone revoke command. Lifecycle cancellation/non-Published also ends detail access, but is not a link-revocation operation. | Whether Slice 3 exposes standalone invalidation; authorized actor, command, audit and failure behavior. | If standalone invalidation is required, authorize the owning Organizer only, make it auditable, and deny the old proof on the next read. This is a proposal, **not** an inference that Organizer issuance authority already grants revocation. | No standalone invalidation command in Slice 3; lifecycle changes still stop detail access. This needs explicit acceptance against the security requirement to support revocation. |
| After invalidation | Invalidated proof cannot authorize detail. | Whether the record remains for audit and what the user-facing unavailable page says. | Retain minimal auditable invalidation fact; use the common safe unavailable result without disclosing why. | Different retention/display policy that preserves non-leakage. |
| New proof after invalidation | Issuance/distribution is Organizer-controlled, but replacement is not defined; no rotation UI is approved. | May the Organizer issue a new proof, and is this a separate command? | Allow a new proof only through an explicit authorized, audited issuance decision; the old proof never becomes valid again. No rotation UI. | Defer reissue, or require a separate future approval. |
| Concurrent active proofs | Not specified; no recipient-bound invitations. | One or multiple active proofs per event? | At most one active proof per PRIVATE event, if issuance/reissue is approved; avoids invitation management. | Multiple active event-scoped proofs with independent invalidation, requiring a larger audit and management contract. |
| Proof transport/verifier | Server-verifiable bearer link and secret-safe transport/storage are required; exact format and carrier are not fixed. | Link URL shape, proof carrier to API, verifier/storage rules, redaction/cache/referrer behavior, and issuance delivery surface. | Specify one opaque event-scoped proof and a secure browser-to-API presentation path in the security contract before implementation; do not log, echo, or place proof in public payloads. | Another reviewed bearer-proof mechanism satisfying the same validity and non-leakage rules. |

The smallest auditable proposal is one event-scoped, bounded proof with an Organizer-controlled issue/invalidate path and no recipient or rotation UI. It remains **unapproved**. In particular, the existing documents do not fix a TTL, grant standalone Organizer revocation by implication, permit replacement, or allow multiple links. Account/guest proof remains separate and is needed only in the later registration slice.

**Conditional PRIVATE issuance/invalidation:** Organizer issuance/distribution must have a secure way to occur, but the documents do not decide whether proof is issued during event setup, through a distinct command, or by another controlled workflow. No issuance, reissue or revoke endpoint is invented here. If standalone commands are approved, their method/route, owner authorization, CSRF, audit, idempotency, response-once proof handling and failure behavior must be added to the authoritative security/API contracts before implementation.

**No separate availability, readiness or gate-list endpoint is necessary for this minimum contract:** availability travels in PUBLIC/PRIVATE detail and authorized management responses; gate association/readiness travels in management detail and transition results. A gate `GET`/`PATCH` may be justified only if an approved gate field or independent screen needs it; none is required by the current minimum configured-gate predicate. No registration action or capacity-count read is supplied. The existing Slice 2 gate-scope endpoint is staff authorization support, not public gate configuration.

## 3. Endpoint authorization matrix

`Allow` is conditional on the resource and lifecycle guards above; `Deny` means no such authority even if the actor knows an ID; `N/A` means the endpoint is not a Slice 3 action for that actor. A valid PRIVATE link is bearer authority for the allowlisted detail **regardless of the visitor's account role**; without it, no role gains PRIVATE public detail by guessing an ID. An owner/admin can separately use the scoped management-detail route. Guest here means a verified or unverified guest; guest OTP does not grant management or PRIVATE detail by itself.

| Actor/context | Create | Management list/detail | Event edit | Gate configure | Lifecycle transition | PUBLIC catalog/detail | PRIVATE detail with valid link | PRIVATE detail without link |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Organizer of event | Allow | Allow, owned only | Allow, state/field rules | Allow, owned | Allow, owned only | Allow | Allow as bearer visitor | Deny on public route; management route remains available |
| Assigned Event Admin | Deny | Allow, assigned only | Allow, narrow Draft/Published fields | Allow, assigned | Deny | Allow | Allow as bearer visitor | Deny on public route; management route remains available |
| Authenticated Participant | Deny | Deny | Deny | Deny | Deny | Allow | Allow | Deny |
| Guest | Deny | Deny | Deny | Deny | Deny | Allow | Allow | Deny |
| Gate/Security staff | Deny | Deny | Deny | Deny | Deny | Allow | Allow as bearer visitor | Deny; separate existing assigned-gate scope is not event management |
| Volunteer | Deny | Deny | Deny | Deny | Deny | Allow | Allow as bearer visitor | Deny |
| Unauthenticated visitor, valid PRIVATE link | Deny | Deny | Deny | Deny | Deny | Allow | Allow | N/A: this context has a valid link |
| Unauthenticated visitor, no valid PRIVATE link | Deny | Deny | Deny | Deny | Deny | Allow | N/A: no valid link | Deny |

Availability/readiness are embedded read fields, not separate authority; unauthorized actors do not acquire management readiness through the public serializer. `view=owned|assigned` is a filter, not a client-supplied grant. Staff grants remain the existing Slice 2 routes and matrix, not a new universal Organizer-only rule.

## 4. Minimum response payloads

These are **field-level proposals**, not approved OpenAPI schemas. All responses follow the common correlation/status/revision/time conventions where applicable; `as_of` is server time. `event_id` and `gate_id` are opaque. Exact nullable/required fields, enum spellings, pagination limits and version/key transport require final API approval. Public fields follow `OPD-02`; no response below contains participant lists, contact/OTP data, QR, audit entries, live occupancy, forecasts, alerts, scanner health, or management internals.

| Payload | Minimum fields and separation |
| --- | --- |
| Management event list | `items[]` with `event_id`, name, lifecycle `state`, scheduled start/end, `time_zone`, and server-derived relationship (`owned` or `assigned`); `next_cursor`, `as_of`, `correlation_id`. No participant or operational aggregates. |
| Management event detail | `event_id`, name/description, `state`, `visibility`, schedule and `time_zone`, approved public fields, Organizer-owned configuration (one registration capacity, opening/closing/manual-close/cutoff and applicable policy), persistent gate references, `readiness` blockers for Publish/Live, `availability`, server-derived `permitted_actions`, `revision`, `as_of`, `correlation_id`. ## 5. Lifecycle and error rules

- `Draft` can be saved partially without a gate; Organizer-only `Draft→Published` requires the full publication validation including a persistent authorized Event–Gate association (`UC-02`, `FR-EVT-002`, `FR-EVT-004`). Organizer-only `Published→Live` independently rechecks that association. Gate existence is not scanner operational readiness.
- Only Organizer transitions an owned event. The [lifecycle table](../requirements/EVENT_LIFECYCLE.md) governs allowed completion/cancellation edges, including Organizer Live cancellation. No clock-driven automatic lifecycle transition is assumed. `Cancelled` stops new registration/check-in in later slices; existing rows remain for audit. No event cancellation by Event Admin.
- Lifecycle `state`, registration-policy availability, and the one `REGISTERED` registration cap are separate. Published policy can be not-yet-open, open, scheduled-close-reached and/or manually closed. Event start is the default close when no explicit closing time exists. Live/Completed/Cancelled are not publicly detail-readable; management can explain their closure. Slice 3 does not know capacity saturation.
- `PATCH` authorizes each field against actor, event relationship and current state. Admin allowlist is exact; no generic Admin PATCH, no ownership transfer, no unrestricted Live edit. Gate setup is a separate action. Material Published edits and all state changes use required audit and atomic failure behavior; high-impact writes check revision and idempotency per the common contract. Timeout is an **unknown outcome** requiring safe read/retry, not proof of rejection.
- Use the common `{code,message,correlation_id,details?,retryable?}` envelope: `400` malformed/field validation; `401` missing/invalid account session on management commands; `403` wrong role/scope/field; `404` unknown or privacy-concealed resource; `409` revision/idempotency/invalid transition; `422` distinguishable readiness or policy rejection; `429` throttling where applicable; `503` dependency or required-audit failure. Final exact code catalog remains an API-contract task. PRIVATE invalid/mismatched/invalidated/expired/non-Published/unknown conditions must all yield the **same** privacy-safe unavailable shape/status and not reveal which happened.
- PUBLIC discovery is anonymous but filters PUBLIC + Published server-side. PRIVATE entry does not appear in catalog and requires proof on every detail read. Server must not substitute an ordinary event ID for proof, expose the proof in response/logs, or leak a PRIVATE event through different errors, timing-sensitive metadata, cache headers, or public counts. Final proof transport/cache controls require security review.

## 7. Exact remaining human approvals

1. **PRIVATE proof lifecycle:** choose independent bounded expiry policy and duration/trigger; decide standalone invalidation command and actor (Organizer authority to issue/distribute does not itself settle revoke), whether reissue is allowed, and one versus multiple active proofs. Confirm invalidated/expired proof never regains authority and all denial outcomes remain indistinguishable.
2. **PRIVATE proof delivery/verification:** approve link route and browser-to-API carrier, server verifier/storage and secure delivery/redaction/cache/referrer behavior. Decide where Organizer issuance occurs; add a separate issue/revoke route only if that workflow is approved. No recipient-bound invitation or rotation UI.
3. **Concrete API/OpenAPI contract:** approve candidate routes and schemas, management list view/default/order/page limits, field requiredness/validation, Organizer lifecycle-sensitive edits, gate-create body and allowed lifecycle states, cancellation reason/confirmation payload, revision/idempotency key transport and retention, exact typed errors and unknown-outcome recovery. These are technical/API approvals constrained by existing product rules, not permission to broaden them.
