## 1. Exact scope and buckets

[ROADMAP_PHASE_2.md](../ROADMAP_PHASE_2.md), row 3, assigns **Organizer event lifecycle + discovery**: Draft/configure/publish/Live/complete/cancel, PUBLIC allowlisted discovery, PRIVATE controlled entry, and registration-availability reasons. Acceptance explicitly covers Organizer-only transitions including cancellation from Live, Admin cancellation denial, Cancelled blocking subsequent registration/check-in while retaining existing rows, and public non-leakage. [SLICE_2_PLAN.md](SLICE_2_PLAN.md), “Slice 2 → Slice 3 boundary,” assigns real event create/edit workflow, publication validation, and gate configuration to Slice 3; the approved lifecycle now requires a configured gate at Publish and independently at Live. This follows the committed Slice 2 identity, owner/Draft, gate-scope, staff-assignment and audit foundation; current Event/Gate rows are foundation records, not working event creation/configuration.

`S-ORG-01`, `S-ORG-02`, the gate-configuration portion of `S-ORG-03`, `S-PUB-01`, and `S-PUB-02` are the primary Phase 1 [screen responsibilities](../design/SCREEN_INVENTORY.md). Slice 3 may display registration **availability** but cannot demonstrate REGISTERED-cap saturation without Slice 4 registration facts. It must not imply the later registration/check-in endpoints already enforce cancellation; it establishes the terminal event state and contracts those slices must honor.

## 5. Slice 3 screen build order and component strategy

**Must build in Slice 3, dependency order after final readiness approval:** (1) reuse verified account/session/CSRF entry and establish the locked application-shell Event + effective Role context with authorized restore/switch/no-context behavior; apply the locally persisted Light/Dark/System mode before rendering and follow OS changes in System; (2) scoped event list and Organizer Draft creation with validation/unknown-result recovery; (3) event detail/edit under the approved Admin allowlist plus one capacity, schedule/zone, visibility, registration opening/closing/manual status and minimum gate configuration; (4) publication readiness and Organizer-only publish/start/complete/cancel controls with configured-Gate checks at Publish and Live and audited, version-safe responses; (5) bounded Organizer-only PRIVATE link issue/revoke/reissue and PUBLIC catalog/allowlisted detail/PRIVATE bearer entry; (6) display distinct registration-policy reasons and safe public failure states without a working registration action or fabricated cap facts; (7) integration and negative UX/API tests for Admin denial, wrong-event, old-proof denial, private leakage, invalid transitions, Cancelled behavior, stale context/assignment and theme-mode rendering. The exact API/security contracts are approved documentation but unimplemented. The list may be implemented before any calendar.

**Design now / implement later:** mobile registration/QR; assigned-gate scanner and unknown-result recovery; Organizer/Admin command-center information hierarchy (registered, checked in, INSIDE, capacity used, forecast, alerts, recent activity) without one card per number; forecast STALE/UNAVAILABLE and uncertainty; alerts, own volunteer tasks and certificates. Use the corresponding future-slice contracts, no fake product data in Slice 3.

**Defer:** full calendar, generic workforce manager, generic alerts/notifications or activity feed, external channels, ornamental dashboard blocks and unapproved 21st.dev code. Six screenshots discussed separately are visual references only; no source URL, component ID or license information was supplied in this repository. See [COMPONENT_SOURCES.md](../design/COMPONENT_SOURCES.md).

For **Slice 3 only**, recommend a minimal reviewed shadcn/ui set **after the final readiness audit and concrete package/accessibility evaluation**: `Button`, form `Field`/`Input`/`Textarea`/`Select` as actual fields require, `Badge` for textual lifecycle/availability, `Alert` for validation/permission/readiness, `AlertDialog` for high-impact transitions, `Table` for the event list if density warrants it, `Skeleton` and `Empty` for loading/no-event states, and `Separator` where structural grouping needs it. Use semantic theme variables, visible focus, text plus status color, restrained borders/surfaces and Lucide icons only when their action meaning is clear. Do not install `Chart`, `Calendar`, `Sidebar`, animation, or a second UI library just to match a reference. Tailwind/shadcn/Lucide are a **direction**, not existing dependencies. Follow the project’s Vite/React architecture rather than copying Next.js imports/demo logic. Final component versions, token values, implementation of the approved theme behavior, bundle and WCAG checks belong to implementation review; no external source component has been adopted by this plan.

## 6. Conflict check and acceptance gate

- **Product-aligned:** Organizer owns/creates and alone transitions/cancels, including Live cancellation; Admin may edit only assigned permitted settings and may not cancel/transfer ownership/grant Admin. PUBLIC Published only is catalog-visible; PRIVATE entry is controlled and non-leaking. A cancelled event blocks future registration/check-in without rewriting existing rows. Registration availability is separate from event state; default/future opening, scheduled/event-start, manual, capacity and Live closure are not conflated. The one capacity is a REGISTERED-registration cap, not a physical gate cap. Gate/Volunteer/Participant surfaces stay scoped. No QR, occupancy, forecasting, alert or certificate functionality is added to Slice 3. These match `OPD-01`, `OPD-02`, `OPD-09`, `OPD-11`, `OPD-12`, `OPD-13`, `OPD-14`, `OPD-17`, `OPD-18` and the [traceability map](../requirements/TRACEABILITY.md).
- **Approved guard clarification:** `UC-02`, `FR-EVT-002/004`, and the lifecycle now require an authorized persistent Event–Gate association at Publish and independently at Live. This was a publication-guard ambiguity, not a logical contradiction; scanner/staff/health readiness is not part of the Slice 3 configured-gate predicate.
- **Documentation drift, not a new product choice:** Phase 0/2 API-file headers say no endpoints are implemented; Slice 2 auth/staff endpoints now exist. This plan classifies from code. The two incorrect `docs/architecture/*CONTRACT/ARCHITECTURE` paths in the request were resolved to their actual locations above; no repository source link uses those nonexistent paths.
- **Locked Slice 3 UX behavior versus visual implementation choices:** Event + effective Role selection/restore and Light/Dark/System switch, local persistence, OS following and pre-render application are approved. Final palette/font/component variants and package choice remain evaluation tasks under [DESIGN_SYSTEM.md](../design/DESIGN_SYSTEM.md), not permission to install packages or invent product behavior.

**Planning acceptance:** this document maps all 18 candidate surfaces plus necessary narrow gate setup and separates EXISTING support from unimplemented Slice 3 contracts. ## Slice 7 finalized operations UI extension

The earlier command-center snapshot/Socket.IO gap is resolved for occupancy by the FINALIZED [Slice 7 contract](../api/API_CONTRACT.md#slice-7-finalized-versioned-snapshot-and-socket-contract). Extend the existing Slice 6 `/operations/{eventId}` screen with visible connection state, dedicated attendance revision, authoritative as_of/last confirmation, sequential reconciliation, revision-gap recovery, stale/out-of-order protection, initial/reconnect REST reconciliation and event-context unsubscribe/abort cleanup. Socket payloads never supply occupancy values. Connected alone does not mean live; reconciliation must succeed. Preserve existing capacity arithmetic, safe permission handling and Light/Dark/System behavior. Alerts, forecasting, volunteer/certificate and departure/correction gaps remain outside this slice.
