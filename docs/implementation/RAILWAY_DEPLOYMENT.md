# Railway deployment adaptations

## Approved Vercel OTP source deployment

For the current Vercel frontend and Railway HTTPS API, OTP challenges use Browser → same-origin Vercel Node function → fixed Railway HTTPS origin → signed source verification → unchanged transactional OTP admission → Brevo. The older all-Railway Docker topology below is an alternative topology, not an OTP source trust boundary for this deployment. No Railway proxy CIDR is required or inferred. See the [source contract and threat reasoning](../security/OTP_ABUSE_PROTECTION.md#signed-gateway-contract-and-threat-boundary).

1. Generate an independent random 32-byte key, represented as exactly 64 lowercase hex characters, through your protected secret-management process. It must differ from JWT/contact/OTP/forecast keys. Keep the value out of commands, chat, logs and Git.
2. Set Railway API `OTP_SOURCE_MODE=signed_gateway` and protected `OTP_SOURCE_SIGNING_KEY`. Remove `OTP_TRUSTED_PROXY_CIDRS` entirely. Keep every existing OTP limit/window, auth/contact/OTP key, database and Brevo variable unchanged. No new migration is needed; retain the existing budget migration.
3. In Vercel Production server variables, set the same `OTP_SOURCE_SIGNING_KEY` and `RAILWAY_API_ORIGIN` to the existing configured production API HTTPS origin (reuse the origin used by `VITE_API_ORIGIN`; do not invent a domain). The gateway requires an HTTPS root origin without credentials, query, fragment or additional path. These variables belong to the Node runtime, never `VITE_*` or browser build arguments. Keep Railway `FRONTEND_ORIGIN` equal to the existing exact production Vercel origin.
4. Use Vercel project root `frontend` and Node 22, deploy the static entrypoints `api/v1/auth/account/challenge.ts` and `api/v1/auth/guest/challenge.ts` with the frontend. Both delegate the unchanged request to the shared gateway in `api/v1/auth/[purpose]/challenge.ts`, using the explicit ESM import `../[purpose]/challenge.js` in their TypeScript source. Vercel traces that import to the TypeScript dependency and emits it as JavaScript; the Node ESM runtime requires the `.js` extension. An extensionless import can pass Vite/Vitest resolution but fail before request processing in production. Keep the shared implementation in place; no additional bundling or routing configuration is required for this import fix. The gateway regression test emits all three modules and loads them with native Node ESM. The static routes require no injected `purpose` query parameter; the shared gateway continues to reject every query string and retains all signing, request validation and upstream handling. The two explicit challenge rewrites precede the SPA fallback. Its source must be `/((?!api(?:/|$)).*)` so `/api` and `/api/...` cannot be rewritten to `/index.html` before Vercel resolves the static function routes; retain the fallback for `/events` and deep links. Verification, renewal, logout, registration, scanner/events and other API calls still use the existing configured API origin. Plain Vite does not run Vercel functions; local gateway testing needs a Vercel function runtime and a separate test API/key. Do not add a production source fallback to accommodate local development.
5. Scope production credentials to Vercel Production only. Preview/Development must use a separate API environment and a separate signing key; never grant previews access to the production key or endpoint. Coordinate Railway/Vercel activation because mismatched or missing keys return generic 503. Rotate both copies together; budget identities and limits stay unchanged.
6. Verify live routing for both purposes, `/events` and a nested SPA route. Check unsigned direct Railway challenge requests, including forged X-Real-IP/X-Forwarded-For/assertion headers, receive generic 503 with no challenge/budget/delivery side effect. Check Vercel replaces spoofed platform metadata, distinct external sources have independent source budgets and one verified source shares its budget across contacts/purposes. Validate normal cooldown, five attempts, five-minute expiry, generic account responses and actual Brevo delivery. Inspect category/status-only logs; never collect raw contacts, IPs, assertions, bodies or keys.

The gateway constructs only its four outbound headers, preserves exact JSON bytes, performs one fetch with redirects disabled and a ten-second upstream deadline, bounds request/response bodies and returns `Cache-Control: no-store`. The API verifies the assertion before OTP admission and never falls back to a proxy/socket/internal source. Protect Vercel runtime access and maintain clock synchronization (at most five seconds future tolerance). Unit/integration/build results are local evidence; actual Vercel routing, metadata rewriting, runtime variables and provider delivery remain deployment acceptance steps.

Deployment instructions, not evidence of a Railway deployment. Baseline `54102e2` plus the existing Slice 12 candidate. Keep the finalized API, schema, nine migrations and domain recovery contracts unchanged. Local verification uses synthetic data only; the existing [security release gate](../security/SLICE_12_SECURITY_REVIEW.md) remains open for public/real-data release.

## Topology and build context

Every Docker build uses the repository root as context, not a workspace subdirectory. Set the documented platform variable `RAILWAY_DOCKERFILE_PATH` per service; retain the image's default command. [Railway Dockerfile configuration](https://docs.railway.com/builds/dockerfiles).

### Forecast Railpack startup

For the forecast service, retain **Root Directory** `/ai-service`, the **Railpack** builder, custom **Start Command** `python forecast-entry.py`, and no **Railway Config File**. The startup wrapper now lives at `ai-service/forecast-entry.py`, inside the service's build root. No dashboard change or builder switch is needed for this fix. Rebuild forecast from a source revision containing the moved file; local, unpublished files cannot appear in a Git-backed deployment. [Railway source root configuration](https://docs.railway.com/builds/build-configuration).

The startup chain is service-root `forecast-entry.py` → Uvicorn `app.main:app`, defined in `ai-service/app/main.py`. The wrapper resolves the service key and requires TLS when binding off loopback unless the [explicit Railway private HTTP mode](#explicit-railway-private-http) is enabled. Keep the existing HTTPS/TLS settings when that mode is absent. Do not replace the wrapper with a direct Uvicorn command that bypasses its startup validation.

Before this fix, the wrapper was tracked only at `docker/forecast-entry.py`, outside `/ai-service`; `ai-service/forecast-entry.py` was absent and was not excluded by `.gitignore`. A Railpack build rooted at `/ai-service` therefore could not supply the file requested by `python forecast-entry.py`, producing `python: can't open file '/app/forecast-entry.py'` before FastAPI loaded. The `/app` path in that error is the runtime working directory, not the repository's root. Changing the command to `../docker/forecast-entry.py` cannot recover a sibling directory omitted from the service build root.

The topology and TLS variables below describe the existing default HTTPS scenario. The explicit private HTTP section supplies its alternative settings.

The repository-root Docker build remains supported: `docker/forecast.Dockerfile` now uses `COPY ai-service/forecast-entry.py ./` and retains `WORKDIR /app` and `CMD ["python", "forecast-entry.py"]`. Both builders use the same startup wrapper; the Docker topology below still requires repository-root context.

Confirm the deployed commit contains `ai-service/forecast-entry.py` and startup logs reach Uvicorn application startup; restarting the old failed image does not add the file. Verify `/internal/health` with bearer authentication over the selected private transport: verified HTTPS by default, or the explicitly enabled HTTP mode below. Startup regression tests isolate the `ai-service` source root and stage the Docker `COPY` paths, execute the wrapper with process handoff intercepted, and import the configured application from each isolated filesystem. Run `python -m pytest ai-service/tests -q` with `PYTHONPATH=ai-service`, or `python -m pytest -q` from `ai-service`. These are local configuration checks, not evidence of a successful Railway deployment.

## Explicit Railway private HTTP

This is a deliberate alternative to private application TLS, not an HTTPS failure fallback. With `FORECAST_SERVICE_TRANSPORT` absent, all existing HTTPS validation, CA/hostname verification, loopback HTTP development and non-loopback TLS requirements remain. Any supplied transport other than the exact `railway_private_http` value (including empty or padded values) fails startup on both services.

Apply these settings later, only after the source change is available to the deployment. This implementation and its tests do not change Railway settings or deploy anything.

The API accepts only the literal URL above or the same URL with one trailing `/`. It rejects credentials (including empty userinfo), other hosts, public domains, IP literals, other schemes/ports, any additional path, query or fragment (including empty delimiters), whitespace and normalized URL alternatives. Python accepts only the explicit `0.0.0.0:8000` HTTP bind in this mode and retains key/file validation. API and forecast must have nonblank platform-provided `RAILWAY_PROJECT_ID` and `RAILWAY_ENVIRONMENT_ID`; forecast additionally verifies its own `RAILWAY_PRIVATE_DOMAIN` equals the allowed hostname. No expected-project/environment variables or invented forecast-domain metadata are introduced. [Railway-provided variables](https://docs.railway.com/variables/reference).

Bearer authentication and Python's constant-time key comparison are unchanged. Node still sends one POST with `redirect: "error"`, a two-second deadline covering headers and streaming body, a 65,536-byte response limit, generic error redaction and the existing response/schema/input validation. The event-scoped public API, permissions, persistence and advisory forecast behavior are unchanged.

**Trust and limitations:** HTTP carries the bearer and forecast input without application TLS. This mode relies on Railway's encrypted private networking and environment isolation. Platform variables are configuration checks, not cryptographic deployment attestation: they can be supplied outside Railway. The API's `RAILWAY_PRIVATE_DOMAIN` describes the API itself, not forecast, and the runtime inputs do not establish the destination's project/environment or enumerate all public domains/proxies. Operators must verify API and forecast belong to the same Railway project/environment, the actual forecast private domain matches, private DNS resolves within that network with IPv4 reachability, and forecast has no public routes. Legacy IPv6-only environments remain incompatible with `0.0.0.0`; this change does not add IPv6 support. [Railway private networking](https://docs.railway.com/networking/private-networking).

The forecast TLS volume is unnecessary in this mode. API `NODE_EXTRA_CA_CERTS` is unnecessary for this forecast HTTP connection; remove it only if its CA is dedicated to forecast and no other HTTPS connection needs it. Do not weaken global Node TLS verification or remove another service's trust material. Public API/frontend HTTPS stays configured as before. Verify authenticated forecast health from the API's private runtime and confirm missing/wrong bearer returns 401; there is no unauthenticated healthcheck exemption.

Local tests cover positive/negative startup and URL cases, both default and private-mode authentication, response validation/redaction/deadline/size bounds for HTTPS, loopback HTTP and the explicit private configuration, and real loopback HTTP redirects (301/302/303/307/308) with a destination request counter that must remain zero. They do not prove Railway DNS, isolation, public-route configuration or deployed connectivity. The existing `docker/railway-verification.yml` and `tests/deployment/private-tls.mjs` remain the separate HTTPS/TLS scenario; do not change that overlay to HTTP. To return to HTTPS, remove the mode from both services, restore the existing HTTPS URL and TLS files/trust, and follow the provisioning section below.

## Private TLS provisioning and trust

For the default HTTPS mode (`FORECAST_SERVICE_TRANSPORT` absent), use an operator-managed private CA and leaf certificate with **DNS SAN `forecast.railway.internal`**, serverAuth extended usage, valid dates, matching private key, CA basic constraints and signing key usage. A CN alone is insufficient. Supply a valid complete certificate chain. Existing Uvicorn TLS flags are used; there is no HTTP fallback or disabled hostname/CA verification. [Uvicorn settings](https://uvicorn.dev/settings/).

Mount an operator-prepared volume at `/tls` on forecast (leaf certificate and private key, optionally public CA), and a separate volume on API containing **only the public CA**. Never upload the CA private key to application services. Keep the leaf private key `0600`, owned by UID 1000, the public certificates readable by UID 1000, and directories traversable only as required. Do not bake material into any image. Ignore rules exclude `.key`, `.pem`, `.crt`, `.secrets/`, `.artifacts/` from Git and Docker build context.

Railway volumes are root-owned and available at runtime, not during build/pre-deploy. Before starting the apps, upload approved files using Railway's authenticated volume tools and prepare ownership. If privileged setup is needed, use a **temporary private maintenance deployment** on the affected service with platform `RAILWAY_RUN_UID=0` and start command `sh -c 'sleep 3600'`; upload files, set ownership/modes, then remove that override and restore the image's normal command/nonroot user before application startup. Never run the API or forecast application as root. Confirm permissions as UID 1000. [Volume files and permissions](https://docs.railway.com/volumes).

Check forecast health from API using its normal CA trust and an Authorization header read from the secret environment/file, never printed or pasted into command arguments. Verify wrong bearer → 401, missing bearer → 401, untrusted CA → TLS rejection, wrong DNS name → hostname rejection. Keep `/internal/*` blocked at the public frontend. Cert renewal is an operator task: provision updated valid files and restart forecast; restart API when CA trust changes, allowing overlap during CA rotation. Do not use synthetic test certificates from this repository's ignored artifacts.

## Migration and provisioning order

1. Reserve frontend F; create **private** managed PostgreSQL and private application services in a fresh compatible environment. Keep all builds rooted at the monorepo. No public DB proxy, API domain or forecast domain.
2. Run the dedicated migration image once, with private admin `DATABASE_URL` and independent runtime-role `PGPASSWORD`. `node docker/migrate.mjs` runs `prisma migrate deploy --config database/prisma7.config.ts` through `npm run db:migrate`, then transactionally provisions eoc_app and grants existing table/sequence access. It rejects runtime-role DDL URLs and unsafe/ambiguous configuration. A nonzero exit blocks application rollout. No reset, seed, automatic organizer creation or migration SQL edit.
3. Verify nine migrations applied, runtime DML allowed, schema creation and `_prisma_migrations` access denied. Repeat deploy is safe; serialize operator migration jobs. Retain stable runtime password when re-running. Runtime image deliberately contains no npm/Prisma CLI: do **not** configure an API pre-deploy `npm run db:migrate`. Railway pre-deploy files/volume changes are not durable. [Pre-deploy behavior](https://docs.railway.com/deployments/pre-deploy-command).
4. Provision private TLS files and identical service key; start forecast, verify authenticated private HTTPS. Start API with eoc_app URL, CA trust and exact F; check readiness. Optional forecast/email-provider degradation must not remove core API availability.
5. One-time controlled account provisioning, only with approved contact/capability: temporarily set the four bootstrap variables plus existing direct database/key config on API and run `node backend/dist/bootstrap.js --confirm` in its private operator shell. This records existing atomic audit evidence. Remove bootstrap variables afterward; never make bootstrap a deployment/start command.
6. Build frontend with `FRONTEND_ORIGIN=F`, start its Railway-selected HTTP Caddy config, attach only its generated public HTTPS domain to `PORT`. Verify browser REST/cookies/CSRF and Socket.IO through that domain before accepting traffic.

## Certificate email, SMTP, observability and recovery

For Railway account-verification/OTP and certificate email, set `EMAIL_TRANSPORT=brevo_api`, `BREVO_API_URL=https://api.brevo.com/v3/smtp/email` and the existing `SMTP_FROM` to the platform sender verified in Brevo. Enter `BREVO_API_KEY` only in protected API service Railway Variables, then redeploy API. Do not put the real API key into local `.env`, `.env.railway.*`, `.secrets`, tracked files, commands or chat. Neither OTP nor certificate email requires an SMTP connection, volume or extra provider SDK in brevo_api mode. Local development retains `EMAIL_TRANSPORT=smtp` and existing `SMTP_URL`/`SMTP_FROM` for both email paths. There is no fallback between transports.

Brevo receives one recipient, unchanged subject/text, and the exact stored PDF as an inline base64 attachment. The request uses the `api-key` header, verified HTTPS, no redirects, a ten-second deadline covering submission and response body, and an 8 KiB response limit. Configure only the official trusted endpoint: the API key, recipient and PDF are sent to the configured URL. A valid single-message 201 acknowledgement means SENT, never recipient receipt. Explicit 4xx rejection (except uncertain 408) means FAILED; 408, 5xx, redirects, unexpected success codes, malformed acknowledgement, timeout and disconnect mean UNKNOWN. No provider bodies/errors or recipient details are logged. Stable attempt correlation is included in a custom header; Brevo chooses its own Message-ID. These choices follow the [Brevo transactional API](https://developers.brevo.com/reference/send-transac-email).

The existing worker, authorization, revocation boundary, leases/fences, three-attempt limit and explicit FAILED-only retries are unchanged. UNKNOWN stays held; no provider lookup, automated reconciliation, provider idempotency guarantee or automatic resend is added.

**Account-verification and guest email OTP use the same selected transport as certificates.** OTP preserves its configured platform sender, recipient, subject `Your verification code`, original text and five-minute expiry instruction; it sends no certificate attachment. Both email adapters share the existing bounded Brevo HTTP implementation. A valid 201 acknowledgement resolves the existing OTP sender; rejection or an ambiguous outcome throws only a generic submission error. The unchanged OTP service records delivery only on success; on an error it consumes the challenge, records its existing failure audit and reports a generic message. The HTTP 202 challenge response still means accepted, not delivered, and is independent of provider latency/outcome. Generation, hashing, expiry, attempt limits, cooldown, proof rules and account/guest privacy are unchanged. There is no OTP resend worker, provider retry, new delivery state machine or SMTP fallback. Phone OTP continues to require its existing SMS gateway.

An existing Railway worksheet with SMTP_URL is a legacy SMTP setup: apply the Brevo variables above in Railway and omit SMTP_URL in brevo_api mode; do not fill the worksheet with a real API key. Local SMTP remains available. Choosing SMTP on Railway still requires the [Railway SMTP prerequisites](https://docs.railway.com/networking/outbound-networking) and provider support.

Existing delivery semantics remain: SENT means submission accepted, not recipient receipt; FAILED retries require current authority and a new bounded durable attempt; UNKNOWN is held for explicit reconciliation, never blindly resent. Revocation before SENDING prevents submission; an already authorized SENDING attempt persists its outcome normally. No new attempt for a revoked certificate. Existing batch/issuance advisory locks, leases, fencing, idempotency and recovery remain in the API process; retain durable keys and PostgreSQL data.

Existing allowlisted JSON logs/traces go to Railway logs; protect platform log access/retention. `/internal/metrics` stays private and authenticated. No OTLP exporter, hosted Prometheus/Grafana or new observability service is implied. Railway log retention, private scraping and external alerting are operational configuration, not verified here.

Local `scripts/backup*.ps1`/`restore.ps1` use Compose and cannot target Railway directly. Configure managed backups/off-host encrypted archives and validate restore against an isolated managed database before production. Never resume workers on a restored copy until email-provider effects and durable delivery state are reconciled; old SENDING/PENDING records are not proof that no email was sent. Railway RPO/RTO, restore/cutover and email-provider reconciliation are **NOT MEASURED**. Earlier local recovery evidence does not certify Railway recovery.

## Three modes and reproducible local verification

| Mode          | Browser / edge                                                         | Forecast                                           | Database / migrations                                                            |
| ------------- | ---------------------------------------------------------------------- | -------------------------------------------------- | -------------------------------------------------------------------------------- |
| Development   | Vite local HTTP; existing VITE_API_ORIGIN / backend exact local origin | Optional loopback HTTP                             | Existing local DATABASE_URL, root npm scripts                                    |
| Local Compose | Caddy's original HTTPS config, loopback 8443                           | Shared API namespace, loopback HTTP + bearer       | Private local PostgreSQL, mounted admin/runtime secrets, existing migrate target |
| Railway       | Public edge HTTPS → frontend HTTP PORT → private api:3000              | Private port 8000, HTTPS or explicit HTTP + bearer | Managed private PostgreSQL, dedicated migration image and restricted runtime URL |

Run synthetic local verification only, never real participant data. Generate existing demo secrets using `node scripts/demo-secrets.mjs`; build application output first. Create short-lived test TLS with `./tests/deployment/setup-test-tls.ps1` (requires already available OpenSSL; never replaces existing files). Linux operators must make the generated leaf readable to the nonroot test container without exposing the CA private key. Stop the local demo stack before reusing loopback ports.

```powershell
$env:DATABASE_URL=(Get-Content .secrets/migration_url -Raw).Trim()
$env:PGPASSWORD=(Get-Content .secrets/app_password -Raw).Trim()
docker compose -p railway-local -f docker-compose.yml -f docker/verification.yml -f docker/railway-verification.yml up --build -d --wait
docker cp railway-local-edge-1:/data/caddy/pki/authorities/local/root.crt .artifacts/railway/railway-edge.crt
$env:NODE_EXTRA_CA_CERTS=(Resolve-Path .artifacts/railway/railway-edge.crt).Path
node --test tests/deployment/migration.test.mjs
node tests/deployment/proxy.mjs
Get-Content tests/deployment/private-tls.mjs -Raw | docker exec -i railway-local-api-1 node --input-type=module
docker compose -p railway-local -f docker-compose.yml -f docker/verification.yml -f docker/railway-verification.yml down
Remove-Item Env:DATABASE_URL,Env:PGPASSWORD,Env:NODE_EXTRA_CA_CERTS
```

The overlay deliberately publishes **test-only** PostgreSQL on loopback 55432 for fixtures; a local test edge simulates Railway TLS termination. Neither overlay is a Railway deployment manifest. Do not use verification overlays in production or globally prune Docker; stop without `--volumes` to retain demo evidence/data. Successful simulation is not evidence of Railway DNS, edge routing, volume upload/permissions, email-provider submission or managed restore.
