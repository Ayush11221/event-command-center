# Railway deployment adaptations

Deployment instructions, not evidence of a Railway deployment. Baseline `54102e2` plus the existing Slice 12 candidate. Keep the finalized API, schema, nine migrations and domain recovery contracts unchanged. Local verification uses synthetic data only; the existing [security release gate](../security/SLICE_12_SECURITY_REVIEW.md) remains open for public/real-data release.

## Topology and build context

Every Docker build uses the repository root as context, not a workspace subdirectory. Set the documented platform variable `RAILWAY_DOCKERFILE_PATH` per service; retain the image's default command. [Railway Dockerfile configuration](https://docs.railway.com/builds/dockerfiles).

| Service    | Dockerfile / command                                                                                                      | Networking                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| PostgreSQL | Railway managed PostgreSQL; no application PostgreSQL Dockerfile                                                          | Private only; port 5432; no public TCP proxy                        |
| migrate    | `docker/migration.Dockerfile`; `node docker/migrate.mjs`                                                                  | Private one-shot job; no domain, healthcheck or restart loop        |
| forecast   | `docker/forecast.Dockerfile`; `python forecast-entry.py`                                                                  | Private HTTPS `forecast.railway.internal:8000`; no generated domain |
| api        | `docker/backend.Dockerfile` final runtime; `node --import ./backend/dist/observability/startup.js backend/dist/server.js` | Private HTTP `api.railway.internal:3000`; no generated domain       |
| frontend   | `docker/frontend.Dockerfile`; `sh /usr/local/bin/frontend-entry.sh`                                                       | Only public service; Railway HTTPS edge → container HTTP on `PORT`  |

Name the private application services **api** and **forecast**: Caddy's backend DNS is fixed to `api.railway.internal`. Verify actual private hostnames in Railway before issuing the forecast certificate. Use a new environment with dual-stack private networking: these images bind IPv4 `0.0.0.0`. Legacy IPv6-only environments are incompatible with these bindings; do not weaken service TLS to compensate. [Private networking](https://docs.railway.com/networking/private-networking/how-it-works).

Use one API instance and keep it awake. It hosts existing recovery loops and event-scoped Socket.IO; multi-instance room distribution has not been implemented. Configure platform `RAILWAY_DEPLOYMENT_DRAINING_SECONDS` to at least 35 for the API (existing shutdown deadline: 30 seconds); see [deployment teardown](https://docs.railway.com/deployments/deployment-teardown). Healthcheck API `/health/ready`; `/health/live` is process liveness. The frontend proxies both. Forecast `/internal/health` remains HTTPS **and bearer authenticated**: verify it privately, not through Railway's unauthenticated HTTP healthcheck. Do not add a public forecast health route.

Additional platform variable: `RAILWAY_RUN_UID` on API/forecast is optional, nonsecret, runtime-only and supplied by the operator solely for the temporary volume-permission maintenance procedure below. Remove it before starting the applications with their image-defined nonroot users.

`PGPASSWORD` is consumed by this migration helper solely to provision the fixed runtime role; it is removed from Prisma's child environment. Administrator authentication comes exclusively from the fully credentialed `DATABASE_URL`. Do not automatically reference the managed service's administrator `PGPASSWORD` into this job. Backend runtime must never receive migration credentials.

File alternatives already supported by the API: `DATABASE_URL_FILE`, `JWT_SECRET_FILE`, `CONTACT_KEY_FILE`, `OTP_KEY_FILE`, `FORECAST_SERVICE_KEY_FILE`, `SMTP_URL_FILE`, `METRICS_TOKEN_FILE`. Each is an optional nonsecret path to protected secret contents, replaces its direct variable and must not be configured alongside it. Forecast similarly supports `FORECAST_SERVICE_KEY_FILE`. Migrator supports existing `DATABASE_URL_FILE` plus `/run/secrets/app_password` instead of Variables-only mode. Preserve local Compose's file-based setup. Bootstrap reads direct application variables; the Railway procedure below uses those.

`PUBLIC_ORIGIN`/`PUBLIC_HOST` are **local Compose/Caddy** controls, not Railway variables. No new WebSocket URL is introduced: the built browser uses F, credentials, `/api/v1/realtime/socket.io`, and websocket transport. Changing Railway runtime variables does not update an already-built Vite bundle: changing F requires rebuilding the frontend and matching backend origin configuration.

## Private TLS provisioning and trust

Use an operator-managed private CA and leaf certificate with **DNS SAN `forecast.railway.internal`**, serverAuth extended usage, valid dates, matching private key, CA basic constraints and signing key usage. A CN alone is insufficient. Supply a valid complete certificate chain. Existing Uvicorn TLS flags are used; there is no HTTP fallback or disabled hostname/CA verification. [Uvicorn settings](https://uvicorn.dev/settings/).

Mount an operator-prepared volume at `/tls` on forecast (leaf certificate and private key, optionally public CA), and a separate volume on API containing **only the public CA**. Never upload the CA private key to application services. Keep the leaf private key `0600`, owned by UID 1000, the public certificates readable by UID 1000, and directories traversable only as required. Do not bake material into any image. Ignore rules exclude `.key`, `.pem`, `.crt`, `.secrets/`, `.artifacts/` from Git and Docker build context.

Railway volumes are root-owned and available at runtime, not during build/pre-deploy. Before starting the apps, upload approved files using Railway's authenticated volume tools and prepare ownership. If privileged setup is needed, use a **temporary private maintenance deployment** on the affected service with platform `RAILWAY_RUN_UID=0` and start command `sh -c 'sleep 3600'`; upload files, set ownership/modes, then remove that override and restore the image's normal command/nonroot user before application startup. Never run the API or forecast application as root. Confirm permissions as UID 1000. [Volume files and permissions](https://docs.railway.com/volumes).

Check forecast health from API using its normal CA trust and an Authorization header read from the secret environment/file, never printed or pasted into command arguments. Verify wrong bearer → 401, missing bearer → 401, untrusted CA → TLS rejection, wrong DNS name → hostname rejection. Keep `/internal/*` blocked at the public frontend. Cert renewal is an operator task: provision updated valid files and restart forecast; restart API when CA trust changes, allowing overlap during CA rotation. Do not use synthetic test certificates from this repository's ignored artifacts.

## Migration and provisioning order

1. Reserve frontend F; create **private** managed PostgreSQL and private application services in a fresh compatible environment. Keep all builds rooted at the monorepo. No public DB proxy, API domain or forecast domain.
2. Run the dedicated migration image once, with private admin `DATABASE_URL` and independent runtime-role `PGPASSWORD`. `node docker/migrate.mjs` runs `prisma migrate deploy --config database/prisma7.config.ts` through `npm run db:migrate`, then transactionally provisions eoc_app and grants existing table/sequence access. It rejects runtime-role DDL URLs and unsafe/ambiguous configuration. A nonzero exit blocks application rollout. No reset, seed, automatic organizer creation or migration SQL edit.
3. Verify nine migrations applied, runtime DML allowed, schema creation and `_prisma_migrations` access denied. Repeat deploy is safe; serialize operator migration jobs. Retain stable runtime password when re-running. Runtime image deliberately contains no npm/Prisma CLI: do **not** configure an API pre-deploy `npm run db:migrate`. Railway pre-deploy files/volume changes are not durable. [Pre-deploy behavior](https://docs.railway.com/deployments/pre-deploy-command).
4. Provision private TLS files and identical service key; start forecast, verify authenticated private HTTPS. Start API with eoc_app URL, CA trust and exact F; check readiness. Optional forecast/SMTP degradation must not remove core API availability.
5. One-time controlled account provisioning, only with approved contact/capability: temporarily set the four bootstrap variables plus existing direct database/key config on API and run `node backend/dist/bootstrap.js --confirm` in its private operator shell. This records existing atomic audit evidence. Remove bootstrap variables afterward; never make bootstrap a deployment/start command.
6. Build frontend with `FRONTEND_ORIGIN=F`, start its Railway-selected HTTP Caddy config, attach only its generated public HTTPS domain to `PORT`. Verify browser REST/cookies/CSRF and Socket.IO through that domain before accepting traffic.

## SMTP, observability and recovery

Outbound SMTP requires **Railway Pro or above**, plus a provider permitting Railway egress and authenticating the configured sender. Redeploy after plan changes. Keep SMTP_URL secret; use the provider's TLS requirements. No provider API substitution is implemented. [Outbound SMTP prerequisites](https://docs.railway.com/networking/outbound-networking).

Existing delivery semantics remain: SENT means submission accepted, not recipient receipt; FAILED retries require current authority and a new bounded durable attempt; UNKNOWN is held for explicit reconciliation, never blindly resent. Revocation before SENDING prevents submission; an already authorized SENDING attempt persists its outcome normally. No new attempt for a revoked certificate. Existing batch/issuance advisory locks, leases, fencing, idempotency and recovery remain in the API process; retain durable keys and PostgreSQL data.

Existing allowlisted JSON logs/traces go to Railway logs; protect platform log access/retention. `/internal/metrics` stays private and authenticated. No OTLP exporter, hosted Prometheus/Grafana or new observability service is implied. Railway log retention, private scraping and external alerting are operational configuration, not verified here.

Local `scripts/backup*.ps1`/`restore.ps1` use Compose and cannot target Railway directly. Configure managed backups/off-host encrypted archives and validate restore against an isolated managed database before production. Never resume workers on a restored copy until SMTP effects and durable delivery state are reconciled; old SENDING/PENDING records are not proof that no email was sent. Railway RPO/RTO, restore/cutover and SMTP reconciliation are **NOT MEASURED**. Earlier local recovery evidence does not certify Railway recovery.

Run synthetic local verification only, never real participant data. Generate existing demo secrets using `node scripts/demo-secrets.mjs`; build application output first. Create short-lived test TLS with `./tests/deployment/setup-test-tls.ps1` (requires already available OpenSSL; never replaces existing files). Linux operators must make the generated leaf readable to the nonroot test container without exposing the CA private key. Stop the local demo stack before reusing loopback ports.

```powershell
$env:DATABASE_URL=(Get-Content .secrets/migration_url -Raw).Trim()
$env:PGPASSWORD=(Get-Content .secrets/app_password -Raw).Trim()
docker compose -p railway-local -f docker-compose.yml -f docker/verification.yml -f docker/railway-verification.yml up --build -d --wait
docker cp railway-local-edge-1:/data/caddy/pki/authorities/local/root.crt .artifacts/railway/railway-edge.crt
$env:NODE_EXTRA_CA_CERTS=(Resolve-Path .artifacts/railway/railway-edge.crt).Path
node --test tests/deployment/migration.test.mjs
node tests/deployment/proxy.mjs
Get-Content tests/deployment/private-tls.mjs -Raw | docker exec -i railway-local-api-1 node --input-type=module
docker compose -p railway-local -f docker-compose.yml -f docker/verification.yml -f docker/railway-verification.yml down
Remove-Item Env:DATABASE_URL,Env:PGPASSWORD,Env:NODE_EXTRA_CA_CERTS
```

The overlay deliberately publishes **test-only** PostgreSQL on loopback 55432 for fixtures; a local test edge simulates Railway TLS termination. Neither overlay is a Railway deployment manifest. Do not use verification overlays in production or globally prune Docker; stop without `--volumes` to retain demo evidence/data. Successful simulation is not evidence of Railway DNS, edge routing, volume upload/permissions, SMTP provider submission or managed restore.
