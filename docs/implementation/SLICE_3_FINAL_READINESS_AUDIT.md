## Non-blocking implementation notes

- The current [Express CORS configuration](../../backend/src/app.ts) allows Slice 2 methods/headers only. Slice 3 implementation must permit its approved `PATCH`, `If-Match`, `Idempotency-Key`, and PRIVATE `Authorization` header where appropriate; this is not a new endpoint or security decision.
- Event fields/revision/published ordering, proof verifier/one-active constraint, replay storage and reviewed migration are not yet in the Slice 2 Prisma schema. Implement them against the existing Event/Gate/assignment/audit foundation with real PostgreSQL transaction/concurrency tests. Do not add Registration, QR, Attendance, occupancy, forecast, alert, certificate or volunteer-task tables here.
- Exact non-link idempotency retention, SQL isolation, visual token/palette/font/component values, package suitability and authentication route layout are implementation-time evaluation choices under the fixed observable API/UX behavior. Do not turn final colors/fonts into product blockers or install a proposed package without a concrete need and review.
- The [role matrix](../requirements/ROLE_PERMISSION_MATRIX.md) leaves a broad role-combination policy TBD; Slice 3 does not need a compound privilege rule. The selected effective role is UI scope only, while each request must independently match owner or current assignment and action. A future feature seeking compounded/cross-event authority would need its own decision.
- Broad older plan wording still calls some paths/provider choices provisional or says tests are not yet implemented ([API plan](../api/API_PLAN.md), [security plan](../security/SECURITY_PLAN.md), [test strategy](../testing/TEST_STRATEGY.md)). The finalized Slice 3 API section and actual Slice 2 routes/suites supersede those dated general-status lines for this slice; they are editorial drift, not a competing Slice 3 contract. No existing file was changed in this audit.
