## 1. Locked PRIVATE-link security rules

- One active opaque, server-verifiable bearer credential per PRIVATE event, never an event ID masquerading as the secret. The controlled access URL contains the credential and is both the discovery route and proof for the **same public-allowlisted detail** of that event while it is **PRIVATE and Published** (`OPD-02`, `FR-DISC-001`). Account login/guest OTP is not needed for viewing. Verified account/guest ownership remains a Slice 4 registration requirement.
- **No automatic time-based expiry or TTL configuration in MVP.** Detail authority ends on explicit Organizer revocation/replacement, when the event ceases to be Published, or when it is no longer PRIVATE. A proof invalidated by revocation/replacement never becomes valid again. Leaving Published is terminal under the MVP lifecycle; it does not create a route to revive an old proof.
- Only the owning Organizer may issue, revoke, or reissue the link. Reissue atomically invalidates the previous active proof and creates one replacement; the uniqueness invariant forbids two simultaneously valid proofs. Assigned Event Admin has no standalone link mutation permission. There is no recipient-bound invitation system or broad link-rotation dashboard.
- The proof grants **no** management, lifecycle, registration ownership, participant, QR, audit, or operational-dashboard authority. A guessed event ID grants nothing. Every PRIVATE detail request rechecks the currently recognized protected verifier, event association, active/revoked state, `PRIVATE` visibility and `Published` lifecycle. Malformed, unknown, wrong-event, revoked, non-PRIVATE, non-Published and otherwise unauthorized attempts receive the **same** safe `404 PRIVATE_UNAVAILABLE` envelope; no existence or reason disclosure.
- Contract choice for safe transport: distribute a link under the configured public application origin of the form `/private#access=<opaque-proof>`. The fragment is not sent with the initial page request. The browser passes the proof **in memory** to `GET /api/v1/discovery/private` using `Authorization: PrivateLink <opaque-proof>`; it does not put it in a query, API path, localStorage or sessionStorage. Strip the fragment from the visible URL after capture; a reload requires reopening the original link. Apply `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, redaction of URL fragments/header values from telemetry, and no third-party analytics on this entry. A configured public origin, never a request `Host` header, builds issuance URLs.
- Generate a cryptographically random non-guessable proof using maintained primitives; persist only a protected non-reversible verifier plus minimal event/status/audit metadata, never the raw bearer secret. Required link state change and audit commit atomically. A short-lived **encrypted** idempotency response record may retain the issuance result for safe same-key replay; this is protected ciphertext, not raw secret storage or a second active proof. Access logs, ordinary audit, errors and management reads never contain the proof or full URL.
- Contract choice for visibility edits: Organizer change from PRIVATE to PUBLIC invalidates the active PRIVATE proof in the same audited transaction, preventing resurrection after a later switch back. A new PRIVATE proof then requires an Organizer issuance command. This follows the approved PRIVATE-only authority without adding a public credential flow.

The current [authentication/RBAC architecture](../security/AUTH_RBAC_ARCHITECTURE.md) says the eventual mechanism must “support expiry,” and the [contract update](SLICE_3_CONTRACT_UPDATE.md) cautions against an indefinite bearer credential. Those statements conflict with the newly locked **no timed expiry** rule if “expiry” means a TTL. The latest human decision resolves the product choice: revoke/replace and leaving Published are the MVP validity endpoints, not a clock. Amend those authoritative/deferred-mechanic passages before implementation; do not silently add a TTL. The [security plan](../security/SECURITY_PLAN.md) also still lists independent expiry as future contract work and needs the same alignment.

## 2. Final Slice 3 endpoint inventory

All exact routes below are **NEW signatures** for `PLANNED` representative event/discovery/gate operations unless explicitly marked `NEW` operation. They are not live. Common request rules: HTTPS JSON under `/api/v1`; opaque IDs; UTC ISO-8601 instants plus event IANA zone; authenticated account session and existing `X-CSRF-Token` for management writes; server-derived ownership/assignment; no client-supplied role or owner. `If-Match: "<revision>"` is a strong event-revision precondition on writes except create. `Idempotency-Key` is a client-generated opaque key on the POST commands identified below. The response envelope includes `correlation_id` and `as_of`; error shape is `{code,message,correlation_id,details?,retryable?}`. Existing Slice 2 authentication, assignment and assigned-gate-scope routes are reused, not duplicated here.

The public allowlist is `OPD-02`/`FR-DISC-001`; Slice 3 cannot truthfully derive REGISTERED count, remaining spots, capacity saturation or `CAPACITY_REACHED` without Slice 4 registration rows.

## 4. Endpoint authorization matrix

`Allow` always means **the specified event relationship and lifecycle guard still pass**. `Deny` is not rescued by knowing an ID or being authenticated. A valid PRIVATE link allows the public-detail serializer regardless of account role; no role gets PRIVATE detail through the discovery route without the link. Organizer/Admin use a separate scoped management read. `N/A` means the cell describes a context that cannot apply.

| Actor | Create/list/detail management | PATCH event | Create gate | Transition | Issue/reissue/revoke PRIVATE link | PUBLIC catalog/detail | PRIVATE detail with valid link | PRIVATE detail without link |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Owning Organizer | Allow, owned only | Allow, Draft/Published | Allow, owned | Allow, owned | Allow, owned | Allow | Allow as bearer visitor | Deny on discovery route; management read remains |
| Assigned Event Admin | Allow list/detail assigned; **deny create** | Allow exact six-field group only, Draft/Published | Allow, assigned | Deny | Deny | Allow | Allow as bearer visitor | Deny on discovery route; management read remains |
| Authenticated Participant | Deny | Deny | Deny | Deny | Deny | Allow | Allow | Deny |
| Guest | Deny | Deny | Deny | Deny | Deny | Allow | Allow | Deny |
| Gate/Security | Deny; existing assigned-gate scope is separate | Deny | Deny | Deny | Deny | Allow | Allow as bearer visitor | Deny |
| Volunteer | Deny | Deny | Deny | Deny | Deny | Allow | Allow as bearer visitor | Deny |
| Unauthenticated public visitor without proof | Deny | Deny | Deny | Deny | Deny | Allow | N/A | Deny |
| Public visitor possessing valid PRIVATE proof | Deny | Deny | Deny | Deny | Deny | Allow | Allow | N/A |

The management-list `view` query is not a role claim: `owned` uses current owner rows; `assigned` uses current active Event Admin assignments. A person with both contexts may request each view, but neither view expands permissions. Assignment/session revocation is checked on every protected request. The public proof does not unlock the management routes.

## 5. Stable error contract

All errors use `{code,message,correlation_id,details?,retryable?}` and no secret, private-event existence, internal stack or participant data. `details` contains safe validation field names only. `PRIVATE_UNAVAILABLE` is a deliberately collapsed privacy boundary, not a diagnostic reason. Internal diagnostics can record redacted categories without revealing proof.

| HTTP | Code | Exact use |
| --- | --- | --- |
| `400` | `VALIDATION` | Malformed JSON, unsupported field, invalid type/range/zone/time relation, bad cursor/page limit, malformed command header or missing required body field. |
| `401` | `UNAUTHENTICATED` | Missing/invalid/expired account session on management routes. Never used to distinguish PRIVATE proof failures. |
| `403` | `FORBIDDEN` | Authenticated actor lacks operation/field permission, including Event Admin transition or link mutation. `CSRF_INVALID` is the separate `403` code for failed authenticated write CSRF validation. |
| `404` | `EVENT_NOT_FOUND` | Unknown/out-of-scope management ID, or unknown/PRIVATE/non-Published request through PUBLIC detail route, with no existence signal. |
| `404` | `PRIVATE_UNAVAILABLE` | **Identical status, code, message and safe shape** for missing, malformed, unknown, revoked, mismatched, wrong-visibility, non-Published or otherwise unauthorized PRIVATE proof. No per-cause public error. |
| `409` | `INVALID_TRANSITION` | Authenticated owner requests a lifecycle edge not in the lifecycle table. |
| `409` | `VERSION_CONFLICT` | `If-Match` revision differs from authoritative event revision; response has safe current revision, not hidden event data. |
| `409` | `IDEMPOTENCY_CONFLICT` | Same key reused with a different fingerprint/actor/action/resource. |
| `409` | `LINK_ALREADY_ACTIVE`, `LINK_NOT_ACTIVE` | Organizer issue while active, or reissue/revoke without active proof. Only owner management commands expose these codes. |
| `422` | `WRONG_LIFECYCLE_STATE` | Otherwise valid edit/gate/link action in a disallowed event state or visibility. |
| `422` | `MISSING_CONFIGURED_GATE` | Publish or Live guard fails because no persistent Event–Gate association exists; safe management readiness identifies the blocker. |
| `422` | `VALIDATION` | Complete, well-formed event configuration fails publication policy (other than the separate gate guard) or cancellation reason is absent/invalid. |
| `503` | `DEPENDENCY_UNAVAILABLE` | Required database/audit commit fails or service is unavailable; mutation does not proceed without required audit. Timeout before response is an unknown outcome, not a new error code. |

For PRIVATE reads, even a malformed/missing `PrivateLink` header maps to `PRIVATE_UNAVAILABLE`, not `401` or a distinct syntax error. Generic infrastructure `503` must not include event-specific facts. `429` remains a generic abuse-throttle category if applied, never a proof-validity oracle. A public API `404` does not reveal PRIVATE versus absent. A `VERSION_CONFLICT` on an authorized management command may provide revision after authorization; unauthorised callers receive only the concealment response.

## 6. Pagination decision

Use the existing architecture's **opaque stable cursor**, not offset/page number. Both `GET` lists accept optional `cursor` and `limit`; default `limit=20`, maximum `limit=100`, invalid values `400 VALIDATION`. Response has `items[]` and `next_cursor` (`null` at end); no total count. Management order is `created_at DESC, event_id DESC`; public order is `published_at DESC, event_id DESC`. The cursor encodes the ordered position and query scope, so it cannot be reused to change `view` or reveal a PRIVATE record. Authorization and PUBLIC+Published filtering apply before page construction. A newly published/edited event can change later pages; the cursor promises stable ordering for a request sequence, not a historical snapshot.

## 7. Idempotency, retry and version rules

- **Required idempotency + revision:** gate create, lifecycle transition, PRIVATE issue/reissue/revoke require `Idempotency-Key` and `If-Match`. Event create requires idempotency but has no prior revision. Keys are scoped to actor/action/event (or create actor/action) and request fingerprint. Same key/payload replays the original status/body; different payload returns `409 IDEMPOTENCY_CONFLICT`. Check an authorized replay **before** treating the now-advanced revision as a new conflict. All affected fact, active-link uniqueness and required audit writes are atomic.
- **Revision-only PATCH:** `PATCH /events/{eventId}` requires `If-Match`, increments revision on success and returns the new revision. No idempotency key is required for this conditional update. After a timeout the client first GETs the authoritative management detail and reconciles, rather than blindly resending with a new revision. GET reads require neither mechanism.
- **Private issuance replay:** return the same access URL on same-key replay for a bounded **24-hour** idempotency window. Keep the active proof's server verifier non-reversible; retain the replay response only encrypted under server-side material, never in logs or raw database columns. After replay retention, stale `If-Match` prevents a second issue/replacement; the Organizer can inspect `has_active_private_link` and intentionally reissue if the URL was lost. This response-cache lifetime is **not** link expiry. On a different-key initial issue while active return `LINK_ALREADY_ACTIVE`; reissue is the explicit atomic replacement operation.
- **Revocation/reissue outcome:** same-key retry returns the original revocation/replacement result; old proof must fail on the next PRIVATE detail request even if the first response was lost. A distinct later revoke/reissue must meet current active state and revision. Session/cookie clearing is irrelevant to PRIVATE bearer proof validity. Never accept a client claim that an old secret was revoked.
- **Unknown outcome:** network timeout does not mean failure. Retry POST with the **same** key and unchanged body/precondition; never generate a new key for an uncertain command. When replay retention has ended, GET authorized management status/revision and reconcile before a deliberate new command. Do not expose the raw active URL through management GET to make recovery convenient.

## 8. Lifecycle and availability constraints

| Transition | Guard and authority | Result in this slice |
| --- | --- | --- |
| Draft → Published | Organizer only; required configuration valid, including one authorized persistent Event–Gate association (`UC-02`, `FR-EVT-002`, `FR-EVT-004`). | PUBLIC enters catalog; PRIVATE needs separately issued valid link for detail. Registration policy may report OPEN or an applicable closure reason, but no registration endpoint exists. |
| Published → Live | Organizer only; independently recheck at least one configured Gate. | Removes event from PUBLIC discovery, ends PRIVATE link detail authority, closes registration by lifecycle. Scanner operation remains Slice 5. |
| Live → Completed | Organizer only; lifecycle guard from authoritative table. | No PUBLIC/PRIVATE detail. Later results/certificates are not implemented here. |
| Draft/Published/Live → Cancelled | Organizer only, explicit confirmation and nonblank reason in this proposed command contract. | Terminal; no PUBLIC/PRIVATE detail, no new later-slice registration/check-in. Existing registration/attendance history is not rewritten. No participant notification in MVP. |

No automatic event transition occurs because of time. An incomplete Draft may be saved, but cannot publish. Gate configuration is a persistent Event–Gate association, not assigned staff, hardware, connectivity, health or scanner readiness. Event Admin can create that association for an assigned Draft/Published event, never publish or start it. Completed/Cancelled have no ordinary reopening or gate/configuration writes in Slice 3.

Lifecycle `state`, registration **policy** availability, and the one `REGISTERED` registration cap remain distinct (`OPD-13`, `OPD-18`, `FR-REG-001`). Public detail exists only for Published and reports the schedule/manual reasons that can be derived from event data. Multiple blockers can coexist; no configured opening means publication opens the policy, no configured closing means event start closes it, and manual closure remains until Organizer reopening. Live/Completed/Cancelled are absent from public detail; authorized management can show their state separately. Slice 3 has no Registration rows, so it never asserts cap usage, remaining places, `CAPACITY_REACHED`, or a functioning registration action.
